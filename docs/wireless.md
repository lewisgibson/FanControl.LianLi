# The L-Wireless SYNC controller

This document describes the Lian Li **L-Wireless SYNC** controller end to end: how Windows sees it, how L-Connect talks to it, every wire format the plugin reproduces, what the plugin does each second and why, and what we haven't supported. It is the reference for `Transport/WinUsbTransport`, `Protocol/Wireless*` and `Devices/Wireless*`, and it is the place to correct if hardware ever disagrees with what is written here.

Everything below was read out of Lian Li's own binaries (L-Connect 3, assembly version 2.1.29; the plugin was first built from 2.1.11 and brought up to 2.1.29 afterwards, and where the two differ this document says so): `lianli.slv3.dll` (the `slv3` namespace: `MasterDevice`, `RfDevice`, `RFController`, `WinUsb`, `RgbEffect`, `Util`), `slv3.models.dll` (`DevTypes`, `AioParams`), `L-Connect.Core.dll` (`LWirelessDevice`, `NumberHelper`, `LWirelessPumpConfig`, `LWirelessLCDConfig`), `L-Connect-Service.exe` (`LWirelessController`), and `LibUsbDotNet.LibUsbDotNet.dll` (`WinUsbRegistry`, `WinUsbDevice`), decompiled with `ilspycmd`. Only protocol facts were taken; no code was copied. Citations are `Class.Method`. **None of it has been confirmed against wireless hardware yet** - the maintainer owns no wireless kit - so every section is a description of what L-Connect does, not of what a fan was observed doing. Where the plugin chooses not to do what L-Connect 2.1.29 does, the section says so, and the list at the end collects those departures.

## The shape of the system

A FLEX or P28 V2 chain's receiver also has a USB port, and plugged into that it is driven directly , not through the dongles, under the same sensor ids; that path is [`protocol.md`](protocol.md), "The FLEX receivers over USB", and a chain the dongles have bound is the dongles' whichever way it is reached.

A wireless UNI FAN group is not on a USB controller at all. The fans carry their own radio; a group of one to four fans is a single RF device with a 6-byte address, and it is **bound** (paired) to a master. The master is the L-Wireless SYNC controller, which plugs into USB as **two separate devices**:

| Role        | VID:PID       | Also accepted | L-Connect name |
| ----------- | ------------- | ------------- | -------------- |
| Transmitter | `0416`:`8040` | `1A86`:`E304` | `SLV3TX`       |
| Receiver    | `0416`:`8041` | `1A86`:`E305` | `SLV3RX`       |

The split is strict and it drives the plugin's design:

- **The transmitter carries every command out.** Fan speeds, pump parameters, lighting, the save-to-flash broadcast, the clock pulse: all of it is written to the transmitter, which puts it on the air.
- **The receiver is the only way anything comes back.** It keeps a table of every device it can hear - including other people's masters - and returns the whole table when asked. There is no per-device query and no unsolicited notification; polling that list is the only telemetry there is.

So one wireless controller in the plugin owns **both** dongles, and neither is useful alone. L-Connect drives exactly one pair - the first transmitter and the first receiver it finds (`WinUsb.GetRFSender`, `GetRFReciver`) - and the plugin drives one pair too: the first transmitter and receiver Windows puts in the same physical device (their container), so two kits plugged in are never crossed, and only when no two share one, the first of each in device-path order (L-Connect takes the first of each Windows enumerates). It logs any further dongle it leaves alone.

Bound devices are not limited to fan groups. The same master carries Strimer light strips, wireless water blocks (HydroShift II), the Lancool 217 Infinity case fans and the V150, and the plugin reads every one of them out of the same device list. The fan groups themselves span every wireless UNI FAN generation: SL V3, TL V2, SL-Infinity Wireless and CL, and since L-Connect 2.1.29 the FLEX range (SL-INF FLEX, TL FLEX, SL FLEX, CL FLEX) and the P28 V2, all of which bind as ordinary fan groups and differ only in their duty floors and, for the LCD FLEX fans, in the screen table the clock broadcast carries.

## Opening the dongles: WinUSB, not HID

Neither dongle is a HID device. Windows binds them to **WinUSB**, so a HID enumeration cannot see them at all - which is why the plugin used to report `scan located 0 HID interface(s)` on a machine full of wireless fans.

Reaching a WinUSB device is not the same as reaching a HID one, and getting this wrong is the single easiest way to break wireless support:

1. **The generic USB device interface is not the door L-Connect uses.** Every USB device registers `GUID_DEVINTERFACE_USB_DEVICE` through the hub driver. For a device whose function driver is WinUSB a handle opened on that path may well reach WinUSB too (libusb opens devices that way), but it is not what L-Connect relies on, so the plugin does not either.
2. **The right door is the interface GUID the device's own driver registered.** A WinUSB INF writes it into the device's hardware key (`...\Device Parameters\DeviceInterfaceGUIDs`, a `REG_MULTI_SZ`, or `DeviceInterfaceGuid` as a single string on older packages). LibUsbDotNet - which is what L-Connect uses - reads exactly that value, enumerates interfaces of that GUID, and opens the resulting symbolic link.

The plugin does the same, through `cfgmgr32`:

1. Enumerate present device instances under the `USB` enumerator whose instance id carries a dongle's vendor and product id.
2. Open each instance's hardware key and read `DeviceInterfaceGUIDs` (falling back to `DeviceInterfaceGuid`).
3. For each GUID, list that interface class **filtered to this device instance**, which yields the path to open.
4. `CreateFile` on that path with overlapped access - WinUSB requires it even for synchronous calls - then `WinUsb_Initialize`.

A device whose hardware key holds no interface GUID is not WinUSB-bound and is skipped: that is the case where Lian Li's driver was never installed, and the honest outcome is "no wireless controller found" , not a failed open.

### Transfers

Each dongle has one interrupt endpoint pair, OUT `0x01` and IN `0x81`, and every packet in both directions is exactly **64 bytes**. There is no report id and no HID framing.

- A **write** is one OUT transfer of one packet.
- A **read** is however many IN packets the dongle has queued. The end of a reply is the first transfer that times out, so the transport gathers packets until a timeout, as `WinUsb.ReadAll` does: it drains the reply to its end even past the length it asked for, keeps that length, and zero-pads a reply that fell short. Anything beyond the length is discarded and logged, once per run of such reads. The drain stops after eight packets past the length asked for - more than a whole 434-byte list page - so a dongle that never goes quiet cannot hold a read open.
- The IN pipe is flushed **before a request is written**, not before the reply is read, so nothing is dropped from the reply about to arrive. The flush only discards what WinUSB has already taken off the pipe; packets still waiting in the dongle's own endpoint are untouched, and it is the draining read that keeps those out of the next exchange. A flush that fails is logged, once per run of failures, and the write goes ahead.

A failed or short write faults the handle, which moves the transport's `Generation` on at once and has the next transfer reopen the device on its backoff, as `WinUsb.RfSend` closes the device on any failed write and reopens it on the next call. The generation moves at the fault rather than at the reopen so that a controller identifying the device (the FLEX receiver) sees it before the next transfer, which is what reopens the path, reaches the device; a controller setting the device up (this one, replaying every device's saved look) waits until the transport's fault latch (`IsFaulted`) says the handle is open again, so nothing is replayed against a dongle still off the bus. A read does not fault the handle: a reply that does not come within the pipe timeout fails that read and nothing more, as `WinUsb.ReadAll` hands back zeros and `MasterDevice` ignores them. Only a read whose native call hangs past its own bound faults the handle. The details are the transport's and are in [architecture.md](architecture.md).

The only recovery step that belongs to the wireless layer is the **cross-reset** (`Devices/WirelessDonglePair`). `WinUsb.RfSend` counts failed writes per dongle (`iSendErr` is an instance property), and since 2.1.29 `WinUsb.RfRead` counts reads answered with nothing (`iReadErr`: a reply whose first byte is zero, which is what a dongle that never replies within the timeout gives; 2.1.11 counted only reads it could not start for want of an open handle). `iReadErr` is a `static` property, so it is one count shared by both dongles: any read that carries something, from either dongle, sets it back to zero, and the fifth empty read in a row across both resets whichever dongle that read was from. After five failed writes in a row to one dongle, or that fifth empty read, the dongle is reset through the _other_ one: `RFController.ResetTx` sends the reset through the receiver, `ResetRx` through the transmitter (`MasterDevice.ResetTx`, `ResetRx`). Writes and reads are counted apart, each count restarts after its reset and on a success of its own kind, and the reset is itself a write to the partner, counted like any other. One consequence, L-Connect's as much as the plugin's: a receiver that answers nothing while the transmitter keeps answering the master query each second is never reset by this rule, since the query's reply keeps the shared count at zero; the reset comes when both fall silent. A reset that fails is logged; the write that triggered it still fails to its caller, and the read that triggered it still returns its empty reply. A read that throws counts as an empty one, as `ReadAll` hands back the zeros it got for a read that failed part way.

## Layer 1: the dongle packet

The first byte of a 64-byte packet is the command.

| Command | Direction | Meaning |
| --- | --- | --- |
| `0x10` | to TX | Carry one 60-byte chunk of an RF payload. Bytes 1-3 are chunk index, channel, receiver slot. |
| `0x10` | to RX | Give me your device list. Byte 1 is how many pages of ten records to send. |
| `0x11` | to TX | Report your own RF address and clock, and work on the channel in byte 1. |
| `0x15` | to either | Reset. L-Connect writes it to the receiver to reset the transmitter (`ResetTx`) and to the transmitter to reset the receiver (`ResetRx`), after five failed writes to, or five empty reads from, the one being reset (see above). |
| `0x16` | to either | Close. `MasterDevice.CloseRecUsb` and `CloseSenderUsb` exist but nothing calls them; the plugin never sends it. |

**Master query** (`0x11`, to the transmitter, `MasterDevice.QuerryMasterMac`). The reply is one packet:

| Bytes | Meaning                                           |
| ----- | ------------------------------------------------- |
| 0     | `0x11` echoed                                     |
| 1-6   | the master's 6-byte RF address                    |
| 7-10  | the master's clock, big-endian, in 0.625 ms ticks |
| 11-12 | the transmitter's firmware version, big-endian    |

L-Connect ignores a reply that does not echo `0x11`. From one that does it always takes the clock (the ticks summed as an `int`, times 0.625, truncated); a clock of zero means the transmitter has not started, and the reply's address is not taken. Otherwise it copies the address over the one it knew, so an all-zero address makes the master **unknown** until the next good reply - and with no master, `RefreshList` reads nothing. The plugin reproduces all three outcomes. Byte 1 is not a parameter of the query but the channel the transmitter is to work on, so this query - which L-Connect sends every second - is also what keeps the transmitter on the master's channel.

**Device list** (`0x10`, to the receiver, `MasterDevice.GetDev` and `RefreshList`). The reply is 434 bytes per requested page:

| Bytes | Meaning |
| --- | --- |
| 0 | `0x10` echoed |
| 1 | how many devices the receiver can hear, which may exceed what the requested pages carried |
| 2-3 | if bit 7 of byte 2 is set: the receiver's firmware version in the low 15 bits. Otherwise a measurement of the motherboard fan header's PWM: `255 * b3 / (b2 & 0x7F + b3)` |
| 4 onwards | one 42-byte record per device, ten per page |

At most the requested pages' worth of records is read, however many byte 1 reports, and a record whose last byte is not `0x1C` is skipped. The next request asks for exactly `ceil(count / 10)` pages - so the request grows when devices appear and shrinks when they go - and the first request asks for one. Bytes 2-3 of the request stay zero: L-Connect fills them only while it forwards the motherboard header's speed, which we haven't supported.

**The record** (`Protocol/WirelessDeviceRecord`, decoded as `RefreshList` decodes it): bytes 0-5 the device's address, 6-11 the master it is bound to (all zero when unbound), 12 the channel, 13 the receiver slot, 14-17 the device's clock in 0.625 ms ticks, 18 the product type, 19 the fan count (ten or more means the SL-Infinity style end cap is on the right, `isINFRightAttach`, and the count is the value less ten), 20-23 the identity of the effect it is running, 24-27 the per-slot fan type codes, 28-35 the per-slot RPM, 36-39 the per-slot PWM, 40 the command sequence it last acknowledged, 41 the marker.

Since 2.1.29 **the high nibble of each RPM's high byte is not part of the RPM**: `RefreshList` masks it off before `RfDevice.InitAttr` reads `(hi << 8) + lo`, so every RPM is twelve bits (0-4095, which every fan and pump reading fits; older firmware leaves the nibble zero, so the mask changes nothing for it). The nibbles carry, on slot 0, four flags (bit 7 `IsSyncLineOn`, bit 6 `IsSyncMbLight`, bit 5 `IsPWMLineOn`, bit 4 `IsFGOn`); on slot 1, the P28 V2's gear and sync line (first fan type 63), or on any other group the per-screen wireless-theme bits (`WiredlessThemeSwitch`, one bit per LCD FLEX screen that shows its wireless theme rather than PC-streamed content, in the firmware's fan order: the service's fan `i` is bit `max(count, 3) - 1 - i`, `FlexLCDSdkHelper.ToThemeSwitchPlayIndex`); and on slots 2 and 3 the device's RF firmware version (`RFVer`, eight bits across the two). Every new-family device reports a non-zero version, so read unmasked they would add thousands of rpm to slots 2 and 3. The plugin masks them all off the RPM and decodes two of them: `IsSyncMbLight` (`WirelessDeviceRecord.LightingFollowsMotherboard`, the state the `0x27` command sets) and the theme bits (`ThemeSwitches`, which decide the `0x29` switch, see "The clock's screen block"); the other flags and the version are display-only in L-Connect. The rule that reads a device reporting no PWM at all while its first fan spins as running at 100 on every slot tests the masked byte, as `RefreshList` does.

## Layer 2: the RF payload

Everything addressed to an actual fan, pump or light is a **240-byte RF payload**, handed to the transmitter as four `0x10` packets carrying 60 bytes each (`MasterDevice.SendRfData`). The packet header's channel and receiver slot are the ones the device reports **now**; a broadcast goes on the master's channel to slot `0xFF`. Payloads share a common front:

| Bytes | Meaning                                                                    |
| ----- | -------------------------------------------------------------------------- |
| 0     | `0x12`, always                                                             |
| 1     | the RF command                                                             |
| 2-7   | the address of the device being commanded (`FF FF FF FF FF FF` broadcasts) |
| 8-13  | the master's address                                                       |
| 14    | the receiver slot the device was bound under                               |
| 15    | the master's channel                                                       |

The RF commands L-Connect uses:

| Command | Name | What it does |
| --- | --- | --- |
| `0x10` | bind and speed | Sets the four slot PWMs, and restates the binding. **The plugin sends this.** |
| `0x12` | select | Highlights a device in L-Connect's UI. |
| `0x13` | print | A diagnostic. |
| `0x14` | clock | Broadcast clock pulse that keeps every device's clock on the master's, and since 2.1.29 carries the date and time, the PC's figures and the LCD FLEX fans' screen table (see "Saving and the clock"). **The plugin sends this.** |
| `0x15` | save config | Broadcast: commit binding and effect to flash. **The plugin sends this.** |
| `0x16` | reboot LCD | For the fans with screens. |
| `0x19` | switch wireless theme | Moves an AIO screen from PC-streamed content to its own theme. **The plugin sends this.** |
| `0x20` | effect data | One chunk of a rendered lighting effect. **The plugin sends this (Lighting build).** |
| `0x21` | AIO parameters | A water block's pump and screen settings. **The plugin sends this.** |
| `0x22` | picture data | An image for an AIO screen. |
| `0x23` | close wifi | Lancool 217 radio off. |
| `0x24` | motherboard sync | Lancool 217 / V150 motherboard PWM follow. |
| `0x26` | light switch | Lighting off. |
| `0x27` | light sync | Since 2.1.29: the device's lighting follows (1 at byte 20) or stops following (0) the motherboard's ARGB header; record byte 28's bit 6 reports it. **The plugin sends this (Lighting build)**, for a device whose L-Connect sync switch is saved on (see "Lighting"). |
| `0x28` | screen colours | Since 2.1.29: the colours of one LCD FLEX screen's wireless theme, in its slot of the 76 bytes at 20. **The plugin sends this** (see "The clock's screen block"). |
| `0x29` | play wireless theme | Since 2.1.29: turns each LCD FLEX fan's screen onto its wireless theme (the mask the group should hold, a bit per screen, at byte 20; record byte 30's high nibble reports it). The LCD FLEX analogue of the water block's `0x19`. **The plugin sends this** (see "The clock's screen block"). |

### Bind and speed (`0x10`)

`MasterDevice.SyncPwm` builds it, and the plugin builds it the same way:

| Bytes | Meaning |
| --- | --- |
| 8-13 | the master's address (`target_master_mac_addr`) |
| 14 | `target_rx_type`: the receiver slot the device reported when it was first taken as bound. L-Connect 2.1.29 assigns 1-13 (`GetRxUnused`); earlier versions went up to 15 |
| 15 | `MasterChannel`: the master's channel |
| 16 | the **bind index**: the device's 1-based position among the bound devices. `0` unbinds it. |
| 17-20 | the four slot PWMs, `0`-`255` |

This is the same command that binds a device, which is why it restates all of that: a speed write is also a statement of which master the device belongs to and where. That is why the plugin never sends it to a device whose latest record names another master, or none - it would bind the device back.

The **bind index** is computed exactly as `SyncPwm` computes it: walk the device table in first-heard order (see below), skip a device that is not bound, is changing effect, or whose record names no master, and number the rest from 1. A device that has moved to another master is still bound in L-Connect's sense and keeps its number, though it is sent nothing. `SyncPwm` pauses 5 ms after each numbered device, sent or not, and so does the plugin.

### When a speed is sent

Once a second, `SyncPwm` sends a device its target PWMs whenever `NeedSyncPwm` says so: whenever any slot the device **reports** differs from its target by more than 5. A speed packet lost on the air is therefore corrected the next second, and a device that already runs its target is left alone. Two special cases, both kept:

- A device reporting no fans is never sent a speed, except the Lancool 217 and the V150.
- A V150 whose target is at or below 10 on any slot is sent it every second regardless.

The plugin adds one condition L-Connect does not need, because in L-Connect a curve always owns every device: only the slots a FanControl control is driving are compared. A device with no control set in FanControl is sent nothing at all.

A target starts as whatever the device reported when it was taken as bound (`RefreshList`: `fans_pwm.CopyTo(target_fans_pwm)`), and a control overwrites the slots it drives. A slot no set control drives carries what the device reports for it and is left out of the comparison: the packet always goes out whole, so a speed sent for a Lancool 217's front pair must not restore a rear fan FanControl has let go of. A drifted clock freezes the driven slots' targets, as the `RFList` getter does, but never a release. When FanControl lets a control go, or closes, the device keeps running the last speed it was sent, as it does when L-Connect exits.

`MasterDevice.SyncControlInfo` also sends the same payload, whatever the speed, to any bound device heard on another channel or receiver slot than the one it should be on - that is what brings it back onto the master's channel, where the clock broadcast reaches it - and so does the plugin, each cycle. Since 2.1.29 that correction first moves a device whose remembered slot is outside 1-13 onto a free slot (`GetRxUnused`). That is re-binding, which the plugin never does: a device bound on slot 14 or 15 by an older L-Connect is corrected back onto the slot it was bound under, as before.

Since 2.1.29 `NeedSyncPwm`'s V150 rule fires every second: the V150 is written as a case device with slot 3 zero (below), and a target at or below 10 on any slot is always resent, so a bound V150 is sent its speed every second, by L-Connect and by the plugin.

## The device table

`Devices/WirelessDeviceTable` keeps every device the receiver has reported, in the order each was first heard, exactly as `MasterDevice.RefreshList` keeps its `rfList`. Each list read:

- **A device heard for the first time is appended.** If its record names this master it is taken as bound (`bind_to_master`): its receiver slot is remembered as `target_rx_type` and its targets start from what it reports. A master dongle's own record (type `0xFF`) goes to L-Connect's separate master list and is never on the table.
- **Every device has a countdown**, `RfDevice.max_live_time` = 30. It restarts whenever the device is heard (`FindDev`), and it counts down on every read - failed reads included, since `RefreshList` counts down before it sends the request - for every device but a Lancool 217, **bound or not** (2.1.29: `RecType[0] != LC217`; 2.1.11 counted down only an unbound device and the V150, and never dropped a bound fan group or water block). Before the request goes out, every device whose countdown has reached zero is dropped, all of them in the same read (`rfList.RemoveAll`), and so is every master unheard that long; 2.1.29 runs the same removal again after the records, which can find nothing new since every device just heard is back at its full countdown, so the plugin runs it once. A device that comes back is appended at the end as a new device and taken as bound again, with its targets started from what it reports, and so takes the last bind index. A locked list drops nothing.
- **Receiver slot conflicts** are counted per device: each read, a bound device is checked against every device of this master on the same receiver slot, as the table stands when its record is reached. Past four, a pair whose addresses differ only in a first byte of `1` is a **ghost**: the `0x01...` address is dropped and never added again (`CheckJustStartDiff`, `ErrMacLst`). Any other conflict L-Connect resolves by unbinding; the plugin logs it and leaves the binding alone. Without a conflict anywhere in a read, every count eases by one.
- **The Lancool 217 and the V150** have their clock compared with the master's (`sys_offset`) at the end of every read, whatever the read dropped (2.1.11 returned straight after a removal and skipped them that read). One more than two seconds off is left out of L-Connect's bound-device list (the `RFList` getter), so its targets are not updated until the clock pulse brings it back; the last targets keep being resent.

**A device that goes quiet.** The table follows L-Connect's, because the bind index in every speed command is a position in it: a driven device unheard for **30 reads** is dropped, the devices after it move up a number, and when it is heard again it is appended and numbered last, exactly as L-Connect 2.1.29 numbers it. Its FanControl sensors are not dropped with it: the controller holds them by RF address, only adds to them, and reads each one from the table by that address, so while the device is off the table its fans read 0 rpm and its coolant temperature reads nothing, and once it is heard again they read again under the ids they had, and the duty its control holds is sent to it at its new number. Nothing is sent to it in between, since it is not on the table to send to, which is also what L-Connect does. So FanControl's fan-failure detection sees a stopped fan rather than a frozen reading, a curve on the coolant temperature does not follow a frozen value, and the user's bindings survive. The plugin reads the list once a second, so the drop takes about thirty seconds where L-Connect, reading three or four times a second, takes about ten.

The plugin also counts, for every device, the reads in a row that did not carry it, for the two cases where a device stays on the table however long it is unheard: the list is locked, or no list is read because the master is unknown (L-Connect reads nothing then and no countdown moves). A device unheard for 30 such reads is marked **lost** and reads 0 rpm and no temperature the same way, and is still driven, as L-Connect drives it, until it is heard again: it is sent its pending commands like any other device on the table, the water block's screen switch and an LCD FLEX group's screen colours included, since `SyncControlInfo` sends to every device on `rfList` heard or not; a look whose sends run out unheard is marked sent for the process (see "The pump"), and a round still under way when the device is heard again is started over with the rest. Either way the sensors of a device nothing reports for thirty days are let go by the plugin's remembered-controller rule ([architecture.md](architecture.md)), not by the table.

Where L-Connect would unbind a device the plugin does not, because we haven't supported unbinding: a device that was first heard unbound and later names this master (`RefreshList`'s "reunbind") is taken as bound and driven; a device beyond this master's eleventh bound (`RefreshList` unbinds at twelve) is not driven.

## What the plugin drives

A device is **driven** when it is bound in the table's sense, its latest record names this master, and a list read of this controller's has carried it (a device restored from the locked list is not driven until the receiver reports it; a lost device stays driven). What each kind gets, following the fan configuration L-Connect's service gives it (`LWirelessController.addSettingDevice`):

| Type byte | L-Connect `DevTypes` | FanControl sensors |
| --- | --- | --- |
| `0` | a fan group (SL V3, TL V2, SL-Infinity Wireless, CL, SL-INF FLEX, TL FLEX, SL FLEX, P28 V2, CL FLEX) | one control for the group, one RPM reading per fan |
| `1`-`9` | `Strimer` | none (lighting only) |
| `10`, `11` | `WaterBlock`, `WaterBlock2` (HydroShift II) | one control for its fans, the pump's control and RPM, one RPM reading per fan (at most three), the coolant temperature |
| `65` | `LC217` (Lancool 217 Infinity) | a front control (slots 0-1) once a front fan is fitted and a rear control (slot 2) once a rear fan is (L-Connect offers the front curve only when `fans_type[0]` or `[1] == 1`, and creates the rear curve only when `fans_type[2] == 1`), one RPM reading per fitted fan (type code `1` in its slot) |
| `66` | `V150` | a front control (slots 0-1), which the app always offers (`V150SubProfile.CreateFrom`), and a rear control (slot 2) once a rear fan is fitted (`fans_type[2] == 1`, the Lancool 217's rule), one RPM reading per fan. L-Connect 2.1.11 drove it as one fan device on all four slots; 2.1.29 gives it a case configuration with the two curves (`addSettingDevice`'s `V150` case) |
| `0xFF` | another master dongle | nothing |
| anything else | `ALL` | driven as a fan device: one control, one RPM reading per fan |

**One control per group** is L-Connect's own granularity: the service computes one duty per device and `LWirelessDevice.SetFanSpeed` repeats it across all four slots (`Enumerable.Repeat(duty, 4)`). A device without fans gets its control only once it reports some, since `NeedSyncPwm` would never write it (the V150 excepted). A water block has at most three fans because its fourth slot carries the pump's RPM and, in the type byte, the coolant temperature (`RFController.GetAioTemp` reads `fans_type[3]`).

Within a run, sensors are only added: a device heard later, or a group reporting more fans, adds its sensors at the end, and the controller raises `TopologyChanged` so the plugin can ask FanControl to refresh (`IPlugin3.RefreshRequested`). Every id is keyed on the device's RF address (twelve lowercase hex digits), so a device appearing or disappearing never re-keys another's saved bindings:

| Sensor              | Id                               |
| ------------------- | -------------------------------- |
| group control       | `LianLi/w<address>/ctl`          |
| V150 front          | `LianLi/w<address>/ctl`          |
| V150 rear           | `LianLi/w<address>/rear/ctl`     |
| water block pump    | `LianLi/w<address>/pump/ctl`     |
| Lancool 217 front   | `LianLi/w<address>/front/ctl`    |
| Lancool 217 rear    | `LianLi/w<address>/rear/ctl`     |
| fan RPM, slot _n_   | `LianLi/w<address>/f<n>/fan`     |
| pump RPM            | `LianLi/w<address>/pump/fan`     |
| coolant temperature | `LianLi/w<address>/coolant/temp` |

The V150's front control keeps the id of the one control the V150 had while L-Connect drove it as a fan device, so a curve bound to it stays bound and now drives the front pair; the rear fan is a new control. Renaming the front to `/front/ctl` would have orphaned every existing V150 binding.

## Fan speed

The wire value is a PWM byte on a **0-255** scale. L-Connect's service maps a duty percent onto it with `NumberHelper.Map(duty, 0, 100, 0, 255)`, constrained and truncated (`startWriteFanSpeed`, `LWirelessDevice.SetCaseSpeed`). In front of that map sit the service's rules, which the plugin applies to FanControl's duty:

1. **A duty of 0 is sent as 5%**, with no floor: `getTemperatureDuty` (fans) and `calculateDuty` (the case devices) return 5 when the curve asks for no speed. 5% is PWM 12. The only exception is a **P28 V2** group, which `getTemperatureDuty` idles at **1%** (PWM 2). A wireless fan is never sent 0, and whether a P28 V2 stops at PWM 2 is not known.
2. **Anything else is raised to a floor** and capped at 100%. The floor is picked per device the way `convertFanType` picks the fan type - from the first slot's family and size, and whether any slot is an LCD fan - and `startWriteFanSpeed` maps each type to its floor (table below).
3. **A CL or CL FLEX group steps off its reserved values**: `NeedSyncPwm` turns 153 and 154 into 152, and 155 into 156, for a group whose first slot is a CL (`CLV1`) or, since 2.1.29, a CL FLEX (`CLV2`) fan.
4. **`6` is reserved** for "follow the motherboard header", and `RFController.SetFansRPM` scrubs it to 0 from an ordinary request. Every duty the rules above can produce maps to 12 or more, so it cannot arise.

| Device | `LWirelessFanType` | Floor |
| --- | --- | --- |
| a group whose first fan is SL V3 (`20`-`26`) | `SLV3Fan120LED` ... `SLV3Fan140LCD` | 14% |
| a group whose first fan is TL V2 (`27`-`35`), with no LCD fan | `TLV2Fan120LED`, `TLV2FanReverse120LED`, `TLV2Fan140LED` | 11% |
| a group whose first fan is TL V2, with any LCD fan (`23`-`27`, `32`-`35`) | `TLV2Fan120LCD`, `TLV2Fan140LCD` | 10% |
| a group whose first fan is SL-Infinity (`36`-`39`) | `SLINFWFan120LED`, `SLINFWFan140LED` | 11% |
| a group whose first fan is CL (`41`-`42`), RL120 (`40`) or empty | `None` | 10% |
| a group whose first fan is SL-INF FLEX (`43`-`50`) | `SLINFFlexFan120LED` ... `SLINFFlexFanReverse120LCD` | 10% |
| a group whose first fan is TL FLEX (`51`-`58`) | `TLFlexFan120LED`, `TLFlexFanReverse120LED` (`InitAttr` sizes every TL FLEX code as 120 mm) | 11% |
| a group whose first fan is SL FLEX 120 mm (`59`-`60`) | `SLV4Fan120LED`, `SLV4FanReverse120LED` | 14% |
| a group whose first fan is SL FLEX 140 mm (`61`-`62`) | `None` (`convertFanType` has no 140 mm branch for it) | 10% |
| a group whose first fan is P28 V2 (`63`) | `P28V2Fan120` | 8% (idle 1%) |
| a group whose first fan is CL FLEX (`126`-`127`) | `None` (`InitAttr` leaves its `DevSize` at 0) | 10% |
| a water block's fans | `CLFan120LED` (fixed by `addSettingDevice`) | 10% |
| an unrecognised type | `None` | 10% |
| the Lancool 217 and the V150, front and rear | (`startWriteCaseSpeed`) | 11% |

Type `27` is a TL V2 140 mm reverse fan with an LCD (`RfDevice.InitAttr` sets `BindLcd` for it), so a group containing one floors at 10%; so does a TL V2 group containing an LCD FLEX fan (`43`, `44`, `47`, `48`, `51`, `52`, `55`, `56`), for which `InitAttr` sets `BindLcd` too.

The fan type codes L-Connect 2.1.29 knows, from `RfDevice.InitAttr`: `20`-`26` SL V3, `27`-`35` TL V2, `36`-`39` SL-Infinity Wireless, `40` RL120, `41`-`42` CL, `43`-`50` SL-INF FLEX (`43`/`44` 120 mm LCD, `45`/`46` 120 mm LED, `47`/`48` 140 mm LCD, `49`/`50` 140 mm LED; even codes reverse), `51`-`58` TL FLEX (`51`/`52` and `55`/`56` LCD, the rest LED; even codes reverse; all sized 120 mm), `59`-`62` SL FLEX (`59`/`60` 120 mm, `61`/`62` 140 mm; even codes reverse), `63` P28 V2, `126`-`127` CL FLEX (`127` reverse). The plugin names a group for its first fan's family and floors it as above; every family is driven the same way, one control per group with one RPM reading per fan.

The **Lancool 217** and, since 2.1.29, the **V150** are written as L-Connect's `SetCaseSpeed` writes them: the front duty on slots 0 and 1, the rear on slot 2, and slot 3 zero. If only one of the two controls is set in FanControl, the other's slot keeps its last value.

Two things L-Connect does here the plugin does not:

- **Smoothing.** `SetFansRPM` averages a new target with the one before it for a second (see "Where the plugin's timing differs"). FanControl owns the curve and its smoothing, so the plugin writes the duty it was given.
- **Speed curves from temperature.** The service's RPM curves and the TL V2 120 LCD's RPM-to-duty formula (`rpmToDuty`) turn a temperature into a duty; FanControl gives the plugin the duty directly.

## The pump

A wireless water block takes a single 32-byte **parameter block**, sent as RF command `0x21` with the block at payload offset 18, bytes 14-15 as in the speed command (`MasterDevice.SendAioInfo`). It carries the pump speed _and_ everything the AIO's screen shows. `RFController.SetAioParams` lays it out:

| Bytes | Meaning                                                                           | What the plugin sends |
| ----- | --------------------------------------------------------------------------------- | --------------------- |
| 0-3   | CPU temperature, CPU load, GPU temperature, GPU load (each capped at 99)          | zero                  |
| 4-5   | the fan speed figure, big-endian (`FanSpeed`)                                     | saved                 |
| 6     | screen refresh interval (`LoopInterval`)                                          | saved                 |
| 7     | whether the pump temperature is shown (`PumpEnable`, set from `IsPumpTempEnable`) | saved                 |
| 8-11  | whether CPU temperature, CPU load, GPU temperature, GPU load are shown            | zero                  |
| 12    | whether the fan speed figure is shown (`FanSpeedEnable`)                          | saved                 |
| 13-24 | three ARGB colours: the title, the value and the unit                             | saved                 |
| 25    | screen brightness (`LcdBrightness`)                                               | saved                 |
| 26    | always 1                                                                          | 1                     |
| 27    | screen theme (`WirelessTemplateIndex`, 0-12)                                      | saved                 |
| 28-29 | **the pump timer**, big-endian                                                    | from FanControl       |
| 30    | screen rotation                                                                   | saved                 |
| 31    | zero                                                                              | zero                  |

Byte 7 is not a pump switch: the service writes it from the carousel setting `IsPumpTempEnable` (`handleSetPumpCarouselSettings`), next to the other figure switches, and the pump runs from the timer alone. Every saved setting is read from L-Connect's pump settings document and carried through, narrowed to its byte exactly as `SetAioParams` narrows it. With no saved settings the plugin uses the block L-Connect starts a new water block with (`addSettingDevice`): refresh interval 2, pump temperature shown, fan speed 2000 hidden, white text, brightness 100, theme 0. The four live CPU and GPU figures are the one part we haven't supported: the plugin has no readings to fill them with, so it sends them as zero and hidden rather than freezing wrong numbers on the screen. A screen L-Connect has in **advance mode** plays content streamed from the PC and never has the wireless theme applied (`LWirelessController` calls `applyWirelessMode` only when `IsAdvanceMode` is false), and L-Connect's own setting handlers (`handleSetPumpLCDBrightness` and the rest) still write the saved brightness, rotation and colours to it through `SetAioParams`, with the theme byte left at 0. The plugin does the same: a screen saved in advance mode keeps every saved setting, with theme 0.

A screen saved **out** of advance mode is switched to its wireless theme first, as `applyWirelessMode` does at startup and whenever a water block binds, so a screen left on streamed content (a switch cut short by sleep, or L-Connect stopped while it streamed) shows its theme again. `RFController.SwitchAioLcdWirelessMode` raises the device's command sequence and queues ten sends; `MasterDevice.SyncControlInfo` sends `0x19` once a pass, with the device's receiver slot and channel at bytes 14 and 15, at byte 16 how many bound devices before it the pass has counted, and the sequence at byte 17, until the device's list record reports that sequence back at byte 40. Byte 16 counts every bound device before it that is not changing effect, whether or not that device has a command of its own pending: 2.1.29's `SyncControlInfo` is a run of independent `if`s that counts every such device at the end of its turn, where 2.1.11's `else if` chain left a device with a pending command uncounted, and the plugin counts as 2.1.29 does. The plugin sends the switch ahead of the parameter block once a second under the device's next sequence (see "The one-second cycle" for how the sequence is shared), and stops when the record carries the sequence or after ten sends, logging which; the record reports nothing about which content the screen shows, so the acknowledgement is all there is to confirm this one by.

The switch goes to a block once per FanControl process (`WirelessProcessState`), marked when the sends end, acknowledged or not, and this follows L-Connect: the service sends the switch when it starts (`ApplyAll`), when the user binds a water block (`handleDeviceBinding`) or changes its pump setting in L-Connect, and when the transmitter dongle is plugged in again (below), and at no other time. It is not sent when a block drops off its table and returns (`RefreshList` makes a fresh `RfDevice` for it, with nothing pending, and nothing in the service reacts), nor in `ResumeSuspend`, which restores only the lighting handover and the effects; L-Connect relies on the block keeping its theme. So a refresh, the block being lost or dropped and heard again, and the receiver faulting and coming back all leave the mark standing, and the plugin's process, FanControl's service, starts at boot as L-Connect's does.

The transmitter is different, in L-Connect and so in the plugin. `MainService.usbDeviceWatcher_Removed` disposes the service's `LWirelessController` when the transmitter leaves the USB bus (`handleWirelessTransmitterRemovedAsync`, `removeConnectedController`), and `usbDeviceWatcher_Inserted` builds a new one two seconds after it returns (`handleWirelessTransmitterInsertedAsync`, `addConnectedController`), which runs `Init` and then, three seconds on, `ApplyAll` in full: `updateBindDevices` over the fresh table, `applyWirelessMode` for every bound block saved out of advance mode, `applyConfiguredWirelessLCDModes` and `reapplyCurrentLighting`. 2.1.11 did the same from its plainer inserted and removed handlers. The receiver has no such controller: `addConnectedController` has no branch for its type (it logs "not supported"), the startup scan (`USBDeviceFinder`) lists transmitters only, and the RF layer reopens the receiver by itself (`WinUsb.watcher_DeletionEventArrived` closes it and `GetRFReciver` opens it again), applying nothing.

The plugin's sight of the transmitter's re-enumeration is its transport's `Generation`, moved the moment the handle is lost. Each time it moves, whichever controller of the process sees it first (at the top of its tick, at the end of its discovery, or on its closing save, before it lets the dongles go) drops every screen switch and screen colour mark of the process, there and then rather than at the reopen, and moves the process's **transmitter lifetime** on (`WirelessProcessState.TransmitterLost`). A look takes the lifetime as it begins and hands it back when it is marked, and everything a controller holds for a look (its rounds, their end, its being done) belongs to that lifetime and is checked against the process's on every pass. So a look begun before the loss, whose sends run on under it and end unheard, marks nothing for the lifetime after it and is started over once its round has ended; a look done under the lifetime before is owed again in every running controller of the process, including one whose own dongles never faulted (FanControl's refresh can put the dongles on new USB paths, and the old controller, still closing on the old ones, counts the loss there while the new one drives the devices on the new); and a look is not begun at all while the transmitter's handle is faulted, since nothing written then reaches the air and L-Connect has no controller at all while its transmitter is off the bus (a round already begun is carried to its end like any command's). Once the transmitter is back, whichever controller drives the devices (the same one, at its reconnect replay, or the one FanControl built meanwhile) sends every device both looks again, as L-Connect's new controller does; a receiver-only fault and reopen sends neither.

A round of the switch still under way when the block is heard again after a loss, or when a dongle comes back, is started over with the block's other commands, as the block may have reset; one whose sends have ended is not. The plugin never binds, and a block the user re-pairs in L-Connect gets the switch from L-Connect at the binding. Like the parameter block, the switch goes only to a water block whose pump FanControl drives.

The pump is commanded by a **timer value, not an RPM**, and a lower timer is a faster pump. L-Connect converts with a piecewise-linear table per generation, clamping the requested speed into range first (`RFController.SetAioPumpSpeed`, `SetH2SAioPumpSpeed`):

| Generation | Type | Range | Table |
| --- | --- | --- | --- |
| First (H2) | `10` | 1600-2500 rpm | 1600-1720: `1500 - (r-1600)*1.667`; 1720-1870: `1300 - (r-1720)*2`; 1870-2000: `1000 - (r-1870)*1.23`; 2000-2300: `840 - (r-2000)*2`; 2300-2400: `240 - (r-2300)*1.8`; 2400-2500: `60 - (r-2400)*0.5` |
| Second (H2S) | `11` | 1600-3200 rpm | 1600-1800: `1590 - (r-1600)*0.95`; 1800-2000: `1400 - (r-1800)`; 2000-2200: `1200 - (r-2000)`; 2200-2400: `1000 - (r-2200)`; 2400-2600: `800 - (r-2400)`; 2600-2800: `580 - (r-2600)*1.11`; 2800-3000: `330 - (r-2800)*1.2`; 3000-3200: `90 - (r-3000)*0.45` |

Each bracket is inclusive at both ends and the earlier branch wins on a boundary, so 2000 rpm on the first generation resolves through the 1870-2000 branch to 841, not through the next one to 840. The plugin reproduces the tables exactly, including that.

FanControl gives the plugin a duty percent, so the plugin spans the block's range linearly and then converts: 0% is the slowest speed the firmware accepts, and 100% is the fastest L-Connect ever drives it - 2450 rpm on the first generation, where every pump curve L-Connect offers tops out (`LWirelessRPMSettingManager`, `MaxSpeed = 2450`) short of the table's 2500, and 3200 rpm on the second. There is no way to stop a wireless pump and the plugin does not try.

`SendAioInfo` sends the block to every bound water block every second, and so does the plugin, to every driven water block whose pump FanControl has set; a pump no control has set is left as it was. Only a change of the pump's duty is logged, not the refresh each second.

## Lighting

L-Connect does not send a wireless device an effect _name_. It **renders** the effect to frames on the PC, compresses them, and streams the bytes to the device, which then plays them back on its own. That rendering is the bulk of `slv3.dll`, and the compressor is a native `tinyuz` entry point (`TuzEnc`). Reimplementing it is out of the question and pointless, because **L-Connect writes the finished result to disk**. Only the Lighting build reads it.

### What is on disk

When L-Connect applies a look it saves the rendered effect to `%ProgramData%\Lian-Li\L-Connect 3\slv3\config\<address>.effect` (`RfDevice.rgbEffect`'s setter), where `<address>` is the device's RF address as twelve lowercase hex digits with no separators. It is `System.Text.Json` output, so the byte arrays are base64 strings:

| Member            | Meaning                                                       |
| ----------------- | ------------------------------------------------------------- |
| `data`            | the compressed frame data, exactly as it goes on the air      |
| `effect_index`    | the effect's 4-byte identity                                  |
| `total_frame`     | how many frames                                               |
| `total_sub_frame` | how many sub-frames, for effects with an inner layer          |
| `led_num`         | how many LEDs the frames address                              |
| `interval`        | milliseconds between frames, fractional                       |
| `sub_interval`    | milliseconds between sub-frames                               |
| `rgb_data`        | null in the saved copy - the uncompressed frames are not kept |

Since 2.1.29 L-Connect also keeps its per-device **"sync to motherboard" switch** for a wireless device (`MainService.handleSetMotherboardARGBSyncRequest`'s wireless branch): a `DeviceSetting<bool>` `{ DeviceID: "aa:bb:cc:dd:ee:ff", Type: "MotherboardARGBSync", Data: true }`, gzipped, at `device\<md5("aa:bb:cc:dd:ee:ff")>\<md5("motherboardargbsync")>.0` (the address as `RfDevice.MacStr` writes it, lowercase hex pairs with colons; `DeviceSettingManager.GetFilePath` lowercases both keys before hashing). Switching it on calls `LWirelessController.SetMotherboardARGBSync(mac, true)`, which is `RFController.SyncMBLightSwitch(mac, isClose: false)`: ten sends of RF command **`0x27`** under a fresh command sequence, laid out like `0x19` with the source at byte 20 (1 to follow the motherboard's ARGB header, 0 to stop), one per pass of `SyncControlInfo` until the record reports the sequence; the record's slot-0 bit 6 (`IsSyncMbLight`) then reports the state. L-Connect re-sends it for every bound device whose setting is saved on when the machine resumes (`ResumeSuspend`), and nowhere else.

The Lighting build reads the setting per device with the effect (`Devices/LConnectWirelessConfiguration`, `FindMotherboardArgbSync`; the other builds never look for it) and, for a driven device whose switch is on, sends `0x27` with 1 at 20 under the device's next sequence up to ten times at every build (the plugin is built anew on every FanControl refresh, so on every wake) and again whenever the device or its dongle comes back. The handover is confirmed by the record's `IsSyncMbLight` bit, not by the acknowledgement alone (the sequence is the device's, and acknowledges whichever command carried it): the first round goes out whatever the bit says, as `ResumeSuspend` sends it regardless; after the round ends, acknowledged or not, the bit is read back for four list reads, a bit still clear gets one more round, and after two rounds the device is logged as left as it is, which is the theme switch's own rounds and readback (L-Connect's `SyncMBLightSwitch` only logs the bit once its sends are done). The device is **still streamed its saved effect** whenever it does not report running it: `MasterDevice.SyncRgbData` streams every bound device whose `effect_index` is not the saved one and never reads `IsSyncMbLight` (the switch is read in `RefreshList` and used nowhere in the streaming path), so under L-Connect a synced device that lost its effect gets it back on its flash, invisible while the switch is on and there when the user turns it off; the plugin does the same. That differs from the wired families, whose `setLightingConfig` is guarded by the switch on every Uni controller, so no look is written to them. The plugin never sends the switch off. Whether a device with the switch on shows the header's colours or its last effect while an effect is still on its flash cannot be verified without one.

`isOuterMatchMax` is not serialised, so after a reload L-Connect itself streams it as 0, and so does the plugin. L-Connect's 12288-byte cap on a compressed effect (`MasterDevice.LzoMaxRgbDataLen`) is checked by only one of its effect renderers and never by its replay, so the plugin accepts any saved effect the stream can carry - 254 chunks of 220 bytes, since the header counts the chunks, itself included, in one byte - and treats only a larger one as corrupt.

### Streaming

`effect_index` is a timestamp L-Connect stamps on an effect when it renders it (`RgbEffect.RefreshIndex`). The device reports the identity of the effect it is running at record bytes 20-23, and `MasterDevice.SyncRgbData` streams whenever that differs from the effect it wants - every loop, for as long as it differs. The plugin does the same on every worker call, for every driven device with a saved effect. While it differs the device is **changing effect** (`changingEffect`): the speed resend skips it and does not number it, until it reports the effect. The effect goes out as RF command `0x20`, one payload per chunk:

| Bytes | Meaning                                 |
| ----- | --------------------------------------- |
| 14-17 | the effect identity                     |
| 18    | chunk index; `0` is the descriptor      |
| 19    | the number of data chunks, and one more |

The descriptor chunk carries the shape of what follows:

| Bytes | Meaning                                                      |
| ----- | ------------------------------------------------------------ |
| 20-23 | the compressed length, big-endian 32-bit                     |
| 24    | zero                                                         |
| 25-26 | total frames, big-endian                                     |
| 27    | LED count                                                    |
| 32-33 | the whole-millisecond part of the frame interval, big-endian |
| 34    | the fractional part, as hundredths (truncated)               |
| 35-36 | the sub-frame interval, big-endian                           |
| 37    | an inner/outer matching flag                                 |
| 38-39 | total sub-frames, big-endian                                 |

Data chunks carry 220 bytes each at offset 20. L-Connect sends the descriptor, then repeats it three more times 20 ms apart, then sends the data chunks in order, then waits 10 ms and asks for a save. The plugin does the same, pausing through its injected delay.

**Where the plugin stops short of L-Connect.** L-Connect keeps streaming, and keeps the device out of the speed resend, for as long as the device does not report the effect, so a device whose firmware never takes it never gets a fan speed. The plugin gives up once the device has gone ten seconds without reporting the effect, over at least three streams tried. A stream the dongle failed to send counts towards that too, so a dongle that keeps dropping a long stream does not cost a stream a second for ever, but only a stream that was sent holds the device out of the speed resend, since a failed one asked the device nothing. It is time rather than a count of streams because every control change brings the next stream forward. It logs that it gave the lighting up and drives the device's fans as usual, and it tries the lighting again when a dongle reconnects or the device comes back after being lost. Lighting never costs fan control.

A **Strimer of type 2 or 4** is re-timed first (`MasterDevice.SyncStrimmer_22`): its frame interval becomes the first type 1 or 3 Strimer's interval times that one's frame count over its own, so the two strips run over the same span. The first such Strimer on the table is used whatever it is bound to, and the new interval stays on the effect, as L-Connect keeps it, once that Strimer is gone.

## Saving and the clock

- **Save config** (`0x15`) tells every bound device to write its binding and effect to flash, so the look survives a power cut. It goes out through `MasterDevice.SaveConfig(1)`: one broadcast and nothing more (2.1.11 paused 200 ms after it; 2.1.29 breaks out of its send loop before the pause, and only the three-send `SaveConfig(3)` of the suspend and service-stop saves still pauses between sends). Two rules trigger it, both reproduced exactly (`Devices/WirelessSaveSchedule`): after an effect stream (`RFController.SaveConfig`), ten seconds later if no stream came in the last five seconds, otherwise ten more; and periodically (`MasterDevice.CheckSaveConfig`), one hour after start and then whenever three hours have passed since the last save, never within thirty seconds of a stream. 2.1.29 also saves on every pass for five seconds after a successful bind, which the plugin never makes. L-Connect also saves three times when the machine suspends (`LWirelessController.Suspend`); FanControl tells a plugin nothing about a suspend, so we haven't supported that save. And L-Connect's service saves when it stops (`MainService`'s stop calls `RFController.SaveCfg`); the plugin's close also runs on every FanControl refresh - every wake, logon and unlock - so it saves on close only when a streamed look is still waiting for its debounced save, rather than write the devices' flash each time.
- **Clock** (`0x14`, `MasterDevice.SyncMasterClock`) is broadcast every second whatever else is happening. It keeps each device's clock on the master's, which is what keeps a multi-device effect in step, and what L-Connect relies on to bring a drifted Lancool 217 or V150 back. Since 2.1.29 it also carries a **220-byte block at payload bytes 14-233** (`MasterDevice.cpuInfoParam`), which is how the LCD FLEX fans (TL FLEX LCD, SL-INF FLEX LCD) get their screens' settings; the next section lays it out.

### The clock's screen block

`cpuInfoParam` is a 220-byte buffer `MasterDevice.SetFanLcdInfo(fixData[50], fansData[168])` fills: the fixed block at 0-49, the screen table at 50-217, two zero bytes after. `SyncMasterClock` writes the date and time into it and copies the whole of it into the payload at 14.

The **fixed block** (`RFController.GetFixedData`) is the PC's figures for the screens to show: CPU and GPU temperature and load, clocks, drive, memory, power, fan and pump speeds, voltages, network throughput (bytes 0-31), then the **date and time** at 32-38 (the year big-endian, then month, day, hour, minute and second, from `DateTime.Now`, so local time), then zeros. On L-Connect's first list read of a run (`RFController.InitSensorDataByWiredLess`) every one of the 50 bytes is 20; from then on the figures are live only while a wireless-LCD group that is not in advance mode is bound (the service's one-second `wirelessLCDSensorPushTick`), and 20 otherwise, with the date and time always current. The plugin sends the date and time at payload 46-52, in local time as L-Connect does, and **every other byte of the fixed block zero**: the live figures are screen content the plugin has nothing to fill with, the same decision as the AIO screen's CPU and GPU figures, and a zero rather than L-Connect's idle 20 so that no screen shows a made-up figure.

The **screen table** (`RFController.UpdateSensorDataByWiredLess`, `Protocol/WirelessScreenTable`) is fourteen slots of twelve bytes, one per receiver slot, slot `s` at `(s - 1) * 12`, so at payload `64 + (s - 1) * 12`:

| Byte | Meaning                                                                          |
| ---- | -------------------------------------------------------------------------------- |
| 0-3  | the theme index of the screen on fan 0-3 (255 = no wireless theme)               |
| 4-7  | that fan's direction in the top three bits and its data source index in the rest |
| 8    | the group's brightness                                                           |
| 9-11 | zero                                                                             |

L-Connect writes an entry for every bound group whose first slot is an LCD FLEX fan (`RecType[0]` of `TLV3` or `SLINFV3` with `BindLcd[0]`: codes 43, 44, 47, 48, 51, 52, 55, 56), on the receiver slot its record reports, and only for slots 1-13 (anything else is logged as out of range and skipped). Two bound groups reporting one slot write over each other's bytes, fan by fan, the later in table order last; L-Connect leaves the slot so (the plugin, which never unbinds, leaves the conflict alone as well, logging it) and colours both groups regardless. The plugin's table is written the same way, but a group's entry counts as carried by a broadcast only when the twelve bytes that went out on its slot are the group's own, the entry it alone would put there: a group whose entry another's wrote over is not coloured while that lasts, since its screens have not been told the theme its colours are for, and holds nothing meanwhile (no round of its colours begins, so its sequence is free, and its theme switch is not held behind colours that are not owed); it is coloured once its entry goes out, which only the user re-pairing one of the two in L-Connect brings about. Two groups that want the same entry are both carried.

The values come from what the user saved for the group in L-Connect (`LWirelessLCDConfig`, the `WirelessLCD` settings document, applied by `LWirelessController.applyWirelessLCDMode`): fan `n`'s theme is `TemplateParams.Theme(n+1)`; its data source is the one saved for that fan under that theme (`TemplateFanSettings["n:theme"]`, else `FanSettings["n"]` when its theme matches), else `TemplateParams.DataType(n+1)`; the brightness is `TemplateParams.Brightness`, or 60 when it is 0; and the direction is `(4 - rotation) % 4 + 1` on `TemplateParams.Rotation` clamped to 0-3 (`toWirelessFanDirection`, `normalizeWirelessRotation`; the saved rotation defaults to 3, so the direction to 2). A group L-Connect has nothing saved for gets 255, 0 and 60 (`InitSensorDataByWiredLess`). The fans are numbered in reverse of the service's fan index, the table's fan `count - 1 - n` for the service's fan `n` (`UpdateSensorSettingByWiredLess`), except on an SL-Infinity or SL-INF FLEX group whose end cap is on the left, which keeps its order. The plugin reads the same document (`Devices/LConnectWirelessConfiguration`, the "L-Connect's files" table) and fills the table the same way for every LCD FLEX group it drives, once a second as part of the clock. It fills it whether or not the group's screens are saved in advance mode: L-Connect's own table keeps the last values it applied, which the plugin cannot know, and the saved template is the closest thing to them; in advance mode the screens play content streamed from the PC and read nothing from the table anyway. What an LCD FLEX screen makes of the block cannot be verified without one.

The table names a screen's theme; the theme's **colours** are sent to the screen separately. `applyWirelessLCDMode` sends them for every fan of a group saved out of advance mode, one fan at a time, after the fan's table entry and the clock that carries it: `RFController.UpdateSensorSettingByWiredLess` saves the fan's settings, refreshes the table, broadcasts the clock, sleeps **1200 ms**, and then `UpdateSensorColors` queues RF command **`0x28`** for the fan, after which it sleeps 600 ms more before the next fan's turn. So a screen has 1.2 s with its theme before the theme's palette reaches it, and only once every fan has had its turn does the theme switch below follow.

The plugin keeps the interval on the injected clock instead of sleeping on the worker (the second's other work goes on meanwhile), and measures it as L-Connect does, from the broadcast that carried the entry the colours are for. Its table carries every screen's theme in the group's one twelve-byte entry, and each time the clock broadcast completes the group keeps what it carried for it: the entry's bytes, the receiver slot it went out on, the transmitter lifetime (see "The pump") and transmitter handle (the transport's `Generation`) it went out under, and the clock read once the last packet was written (`Devices/WirelessScreenEntryPublication`).

A screen's round begins only while that is still the entry the group needs (the same bytes on the same slot, as the table holds them this cycle, on the transmitter as it is now) and 1.2 s have passed since the broadcast completed. The same entry carried again by the next second's clock keeps the first broadcast's time, so the periodic clock does not push the wait along; anything else is a new publication, from the next broadcast that completes with it: the group reporting a fan more or fewer (which renumbers every screen, since the table numbers them in reverse), a theme or brightness change, another receiver slot, the transmitter's handle lost since (whether the loss is counted at the next tick or the handle was reopened by an ordinary transfer inside the same cycle), a transmitter lifetime counted by any controller of the process, and the group or a dongle back after a loss, which starts the group's commands and the publication over. A broadcast that completes carrying nothing for the group (its record naming no master for a while, a receiver slot outside 1-13, no LCD fan in its first slot, or its entry written over by another group's on the same slot) withdraws the publication, as L-Connect's fresh table carries nothing for it either, so an entry that goes and comes back waits its 1.2 s from the broadcast that restores it; a group reporting no fan is carried with an empty entry, which the same rule treats as any other entry the group does not need. The process's mark of a colouring already done stands through all of that. The pass reads the transmitter lifetime once, as it takes the look up, judges the publication under that one and stamps the round with the same, so a loss another controller counts while the pass runs leaves the round under the lifetime its readiness was judged under, which the next pass finds passed and starts over.

L-Connect's date and time in the clock are `DateTime.Now` read before `SendRfData`, and its sleep starts after `SyncMasterClock` returns, so the plugin reads the clock twice as well, once before the send for the bytes and once after the last packet for the wait: the four packets' writes, up to 100 ms each, are no part of the 1.2 s. The first screen's round so begins on the first tick at least 1.2 s after the broadcast that carried the entry completed (the third tick, at one a second); a later screen's round begins in the pass the earlier's ends while the entry is unchanged, and waits the new entry's own 1.2 s when it is not; and the theme switch is held back while the group's colours are owed and not yet done. Nothing holds the switch indefinitely: under a stable lifetime the group's entry is published by the next clock that completes, the interval passes, each screen's round ends in at most ten sends and the colours are done; a transmitter that cannot carry them holds the switch no longer than it holds everything else; and a group that disappears, loses its slot, reports no fan or has its entry written over by another group's is one the colours are owed for in no cycle, so nothing holds its switch.

`UpdateSensorColors` queues the command as ten sends under a fresh command sequence, laid out like the water block's `0x19` (device, master, receiver slot and channel at 14-15, the bound count at 16, the sequence at 17) with a 76-byte buffer at 20 (`RfDevice.sendColors`, a fresh one per fan): a 19-byte slot per screen in the table's fan order, the fan's own slot holding six colours as red, green and blue bytes and then a change marker, the other slots zero. The marker is drawn at random from 1 to 253; the plugin takes it from the round's sequence, which differs between rounds as a random does. The six colours are chosen by `GetWiredlessUserColors` from the eight a theme has, by how many the theme uses (`WiredlessFansInfo.iColorNum`): themes 0, 1, 2, 4, 5, 7, 11 and 12, and any past L-Connect's table, use five, sent as the two graph colours, the title, the data and the unit, and the unit again; 3, 6, 8, 9 and 10 use four, sent as the first graph colour, the three fonts, then the data and unit shadows; 19 to 28 use three, sent as the three fonts and then the three shadows of L-Connect's own table for the theme, never the saved ones; 13 to 18 use none, and the buffer carries only the marker. The eight come from the fan setting saved for the theme (the same `TemplateFanSettings["n:theme"]`, else `FanSettings["n"]`, that gives the data source; `WirelessFanInfoDto`'s colours are packed `0xAARRGGBB`, 0 when absent) or, with none saved, from L-Connect's table for the theme (`RFController.GetWiredlessThemeDefColors`, which the plugin carries in `Protocol/WirelessThemeColours`).

The plugin reads the colours with the rest of the screen settings and sends them (`Devices/WirelessController`, `RestoreScreenColours`) for every group it drives with a saved, non-advance configuration on a slot the table has, in the cycle after the clock and before the theme switch once the interval above has passed, one screen per round under the device's next sequence: a round ends on the acknowledgement or the tenth send (the record reports nothing about the colours, so the acknowledgement is all there is to confirm one by) and the next screen's round starts in the same pass while the group's entry is unchanged, so the sequence is held from screen to screen and the theme switch cannot take it between two; once every screen has had its round the group is logged as coloured.

L-Connect colours the screens when its service starts (`applyConfiguredWirelessLCDModes`), when the user binds a group or changes a screen setting in it, when a group first gets a saved configuration (`addWirelessLCDConfigIfApplicable`), and when the transmitter dongle is plugged in again, since its service builds a new controller for it whose `ApplyAll` runs `applyConfiguredWirelessLCDModes` again (see "The pump" for the watcher path), and at no other time: not when a group drops off its table and returns, and not on a resume. The plugin does it once per FanControl process for a group, marked when the last screen's sends end, and as with the water block's screen switch a refresh, the group being lost or dropped and heard again, and the receiver faulting and coming back all leave the mark standing, while the transmitter's handle being lost drops every mark and the colours are sent again once it is back, by the same rule and lifetime as the switch; the record gives no evidence of the colours a screen holds, and L-Connect relies on the group keeping them. A colouring still under way when the group is heard again after a loss, or when a dongle comes back, is started over with the group's other commands, as the group may have reset; one whose rounds have ended is not. A screen's round keeps the slot and colours it started with, as `sendColors` is filled once per fan, and is the device's to finish (see "The one-second cycle"): a group that reports fewer fans meanwhile is done once every screen it still reports has had its round, while the round in flight for a screen it no longer reports is sent to its end and frees the sequence. What an LCD FLEX screen makes of the colours cannot be verified without one.

The table tells a screen what to show; it does not switch a screen that is off its wireless theme back onto it. That is a separate command, and `applyWirelessLCDMode` ends with it: for a group whose saved configuration is not in advance mode it calls `FlexLCDSdkHelper.TryRestoreWirelessThemeSwitches`, which reads the group's theme bits from its record (`RfDevice.WiredlessThemeSwitch`, the slot-1 nibble), and for every one of the group's `FanNum` fans whose bit is clear calls `RFController.PlayWiredlessThemeSwitch(mac, fan, isOpen: true)`. That queues ten sends of RF command **`0x29`** under a fresh command sequence, laid out like the water block's `0x19` (device, master, receiver slot and channel at 14-15, the bound count at 16, the sequence at 17) with the mask the group should hold at byte 20 (`WiredlessThemeSwitchTarget`: the bits reported with the fan's bit set), one send per pass of `SyncControlInfo` until the record reports the sequence. The helper then waits up to four seconds (twenty 200 ms polls) for the record's bits to match the target, queues the same switches once more if they do not and waits four seconds again, and once they match asks every device to save (`RFController.SaveCfg`), so the switch survives a power cut. L-Connect runs this at its start for every bound LCD FLEX group saved out of advance mode (`applyConfiguredWirelessLCDModes`) and on every settings change; a group with nothing saved, or saved in advance mode, is left as it is, and a group reporting no fan has nothing restored and nothing decided (the helper returns for a `FanNum` of 0, as `applyWirelessLCDMode` returns for a count of 0 before it).

The plugin does the same (`Devices/WirelessController`, `RestoreThemeSwitch`): once a second after the clock, for every driven LCD FLEX group with a saved, non-advance configuration whose record shows a screen off its theme, it sends `0x29` with `WirelessProtocol.ThemeSwitchesForAllScreens` (the reported bits or-ed with every fan's bit, fan `i` at bit `max(count, 3) - 1 - i`) under the device's next sequence, up to ten times; reads the bits back for four list reads; sends one more round of ten, under the next sequence again, if they still fall short; and on a match sends the save broadcast (the plugin's one-send save) and logs it, or logs that the screens were left as they are after two rounds. A group that for a while reports no fan, its first slot still naming an LCD FLEX fan, has no screen whose bit says anything, so its switch is left pending rather than taken as done (a target of no bits over bits of none is not every screen showing its theme), a round of it already under way is sent to its end, and it is decided against the bits the screens report once the group reports a fan again. A group whose lighting handover (`0x27`) is still being sent waits for that round to end before its switch starts, since the two cannot share the device's sequence (see "The one-second cycle"). A group heard again after being dropped, or carried by a dongle that came back, is switched again, as L-Connect switches it again when it binds.

The fan-index arithmetic has one wrinkle in L-Connect: `TryRestoreWirelessThemeSwitches` converts each logical fan to its bit with `ToThemeSwitchPlayIndex` and then hands that converted index to `PlayWiredlessThemeSwitch`, which converts it again (`Math.Max(FanNum, 3) - 1 - index`) before it sets the bit and updates the fan's table entry, so for a group whose clear bits are not symmetric it sets the wrong fan's bit and reports success; the plugin sets every fan's bit as the check intends, which is the same mask whenever every screen is off (the case a mode change cut short or a reset leaves) and the right one otherwise. Which fan a bit is cannot be verified without the hardware; the two readings differ only for a group of one or two fans.

## The RF channel

The master works on channel 8 unless L-Connect saved another. `RFController.Init` queries the master first, then reads `slv3\config\<master address>.config` for **that** master (`GetChannel`): the channel as a decimal number, which 0, an empty file or an unreadable one leaves at the default. The plugin does exactly that when it first learns the master's address, and again if the address changes, so a file left by another master is never used. The channel goes out in every master query - which re-asserts it every second, and at once after a dongle is reopened - in byte 15 of every addressed payload, and in the header of every broadcast. FanControl builds a new controller on every refresh (each wake, logon and unlock), and the first query goes out before the master is known, so the process keeps the channel it last drove the master on and a new controller starts on it: the transmitter is put on channel 8 only on the first start, as L-Connect does it only when its service starts. Once the master answers, a channel L-Connect saved still wins, then the one kept from before the refresh, then 8.

When another L-Wireless controller is in radio range, the receiver hears its master too: every record of type `255` is a master, kept in a list of its own with the same thirty-read countdown as a device (`masterList`). Once a second the plugin does what `MasterDevice.CheckChannelConflict` does. The masters are ordered by address and each place has a channel: 8 for the first, then 12, 16 and so on. If this master reports an even channel other than its own place's, it moves there for this run (`SwitchChannel`), and the ordinary re-homing brings its devices after it. The even channels are the ones L-Connect hands out itself. A channel the user chose in L-Connect is odd (`ChangeChannel` refuses an even one) and is never moved. Like L-Connect, the plugin does not save the move, and makes it once rather than on every read until the master's record shows it. Since 2.1.29 the check is skipped altogether while the device list is locked (`Run`: `if (!lock_list) CheckChannelConflict()`), and so is the plugin's.

### The locked list

L-Connect lets the user lock the device list (`RFController.LockDevice`), which saves the table - every device naming this master, in order - to `slv3\config\savedDevices.config`, a JSON list of its `RfDevice` objects with the byte arrays as base64. 2.1.11 wrote a plain array; 2.1.29 serialises with `ReferenceHandler.Preserve`, so the root is an object `{"$id":"1","$values":[...]}` and every object in it carries an `$id`, with the byte arrays still base64 strings and every member the plugin reads (`mac_addr`, `master_mac_addr`, `channel`, `_rx_type`, `_target_rx_type`, `dev_type`, `fan_num`, `isINFRightAttach`, `effect_index`, `fans_type`, `fans_pwm`, `target_fans_pwm`, `MasterMacStr`) unchanged. The plugin reads both shapes.

At startup `RFController.CheckLockAndInitData` restores it when the first entry names the master just queried, and while it is locked `RefreshList` takes no newly heard device, keeps each device's saved product type and fan types (a water block's and a case's slots are still read, since they carry what is fitted and the coolant temperature), checks no receiver slot, and drops nothing. The table's order is the bind index every speed command carries, so the plugin restores it exactly: the first time it learns the master it reads the file, and if the list is locked for that master the table becomes that list, every device bound at the receiver slot and speeds it was saved with, and it keeps those rules for as long as the list is locked. A device paired after the list was locked is left alone until it is unlocked, as L-Connect leaves it. Unlike L-Connect, the plugin sends a device on the list nothing - no speed, whose command restates a binding - until the receiver has reported it at least once, since a saved pairing is no evidence the device is still paired: the plugin never binds or re-pairs anything. When no device on the list names this master any more, L-Connect unlocks and deletes the file; the plugin stops keeping the lock too, but leaves L-Connect's file where it is.

## The one-second cycle

`Devices/WirelessController` is `MasterDevice.Run` on the plugin's worker. Each call to `PollRpm` is one `RefreshList` (one list read, nothing without a master). Each call to `ApplyPending` runs, when a second has passed since the last, the one-second block of `Run` in its order - the speed resend (`SyncPwm`), the lighting handover of a device whose sync switch is on (`SyncControlInfo`'s `0x27`), the periodic save check (`CheckSaveConfig`), the master query (`QuerryMasterMac`), the water blocks' parameter blocks (`SendAioInfo`, with the screen switch `0x19`), the clock (`SyncMasterClock`), the LCD FLEX screens' theme colours (`SyncControlInfo`'s `0x28`) and their theme switch (`SyncControlInfo`'s `0x29`) - and then, on every call, the effect streams (`SyncRgbData`) and the debounced save. Time comes from the injected clock and every pause from the injected delay.

The four commands sent under a command sequence share one mechanism (`Devices/WirelessDeviceCommand`, with the sequence itself on `Devices/WirelessDevice`), built on how the device acknowledges them. In L-Connect a device has one target sequence (`RfDevice.targe_cmd_seq`): every command `RFController` queues raises it, every pending command's sends carry it at byte 17, and the device acknowledges by reporting the sequence it last received at record byte 40 (`RefreshList` reads it into `cmd_seq`), at which point `SyncControlInfo` ends every pending command for the device at once, whichever of them the device received: a `0x27` lost on the air while a `0x29` got through counts as acknowledged, and is never sent again.

The plugin keeps the one sequence per device and takes the collision out: the commands are sent one at a time per device, in the cycle's order (the handover, then a water block's screen switch, then an LCD FLEX group's screen colours, then its theme switch), each round under the device's next sequence (the one after the last round's, or after the one the record reports for the first; 1 to 254 as L-Connect wraps it; never the one the record reports now), one send a second, and a round ends on the acknowledgement or the tenth send, freeing the sequence for the next command in the same cycle. A reported sequence therefore acknowledges exactly the command that carried it. The two commands whose result the record reports (the theme bits for `0x29`, the `IsSyncMbLight` bit for `0x27`) are confirmed by that result, read back after each round, with one more round when it is missing; the screen switch and the screen colours, whose result the record does not report, end on their acknowledgement.

A round, once begun, is the device's to finish, not its command's caller's: at the top of every second, before anything else the second does for the devices, the controller services every round under way (`ServiceRounds`), as `SyncControlInfo` services every pending command in one place, whatever else the second did for the device. The device hands back the round's next send, or ends the round because its record reports the sequence or the sends are out, and keeps how it ended for the pass that next services the command (`WirelessDeviceCommand.Ended`); the command's own pass then only takes that end, or begins the next round with its first send where the command belongs in the cycle. So a command whose caller has stopped calling it, or whose conditions have changed under it, still runs to its end and frees the sequence: a water block's screen switch mid-round when FanControl releases the pump control (`SendAioInfo` sends the pump nothing then, but the round goes on, and its end is taken and logged on the pass after the device ends it, with the control still released), and an LCD FLEX screen's colours mid-round when the group reports fewer fans, down to none, which the count-driven colouring would otherwise never look at again. The device's one sequence is never held indefinitely by a round nothing finishes. Nothing is sent to a device that is not driven (one whose record names another master), whose round resumes when it is driven again.

Each device's work, and each broadcast, is isolated: a failure is logged when it starts and when it ends - not every second - and costs that device that second, never the others. A dongle the transport lost its handle to and has reopened (its `Generation` moved on at the fault; the reopen happens inside a later transfer of the cycle, on the backoff, and until the transport's fault latch clears nothing is replayed, since a look tried against a dead transmitter would be sent and given up on, and a round of a command acknowledged by a record no read has refreshed) re-runs the plugin's registered replay and the one-second block at once, frees every device's command sequence so a round cut short is started over, and starts each LCD FLEX group's screen entry publication over, so its colours wait their 1.2 s from the clock the reconnect sends. Everything a reset device may have lost that its record reports on - its speed, its effect, its lighting source, its screens' theme switches - is resent by the ordinary comparison against what it reports; a water block's screen switch and an LCD FLEX group's screen colours, which the record does not report on, keep their process marks after the receiver's reopen, as L-Connect sends neither again after a resume (`ResumeSuspend` restores the lighting handover and the effects only), and are sent again after the transmitter's, since its loss dropped every mark the moment a controller saw it, and every controller checks the looks it holds as done against the lifetime on each pass, as L-Connect's service rebuilds its controller for a transmitter plugged in again (see "The pump").

**Construction** asks for the master up to three times, then reads the list until two reads in a row agree, half a second apart and at most four reads: two and a half seconds of waiting at most, bounded by count, not by the clock. L-Connect does not wait - `MasterInite` ignores the query's result and `Run` keeps going - so the wait is the plugin's, there so that FanControl's first load has the devices that are already on the air rather than one refresh each. A master that does not answer leaves a controller with no sensors that keeps asking every second, and the devices appear, with a refresh, once it answers. Construction never throws for a silent or failing dongle.

### Where the plugin's timing differs

L-Connect's loop runs about every 300 ms. It reads the device list on every pass once half a second has gone since its one-second block, and again at the end of `SendAioInfo`, so three or four times in each cycle of about 1.3 s; it sends the channel and slot corrections and the screen-mode switch (`SyncControlInfo`) on every pass; and it keeps the one-second block to once a second. The plugin runs everything on the one-second worker tick, and reads the list once a second however often FanControl wakes the worker, so a list read, a correction or a screen switch goes out once a second rather than about three times. An LCD FLEX group's screen colours, which L-Connect queues 1200 ms after the clock that carried the screen's theme has gone out, begin on the first tick at least 1.2 s after the clock that carried the group's current entry completed: about two seconds at one tick a second, never less than L-Connect's interval, and measured from the broadcast's completion as L-Connect's sleep is (see "The clock's screen block"). Every rule that counts list reads keeps its count but not L-Connect's time: a device or another master unheard is dropped after about thirty seconds rather than ten, and a receiver slot conflict is logged after about five seconds rather than one and a half. None of that changes what is driven: every correction is resent until the device reports it, and the screen switch is acknowledged by the device.

L-Connect also smooths a new speed for one second (`SetFansRPM` puts each target into `fans_pwm_list` and `SetFansPwmFromAvg` sends the average of the last two). The plugin sends FanControl's value as it is, because FanControl already applies the response time and step settings the user chose, and a second layer of smoothing would change what those settings do.

One water block or group whose saved settings are incomplete falls back alone; the others keep theirs. The service's own `loadSettings` catches and logs the same way. The curve files are not read: FanControl owns the curves.

## What we haven't supported

- **Binding, unbinding, re-pairing, or moving a device to another master.** Pairing stays L-Connect's job. The plugin never sends a bind index of 0, and never sends anything to a device whose record names another master or none. Where L-Connect would unbind a device - one first heard unbound that later names this master, one past the eleventh bound, one sharing a receiver slot - the plugin leaves the binding alone.
- **Motherboard sync.** The reserved PWM `6`, the `0x24` command and the forwarding of the motherboard header's speed (`FgSync`, `SyncFgPwm`) are not used: the plugin keeps every device under software control.
- **Live CPU and GPU figures on the AIO screen** and in the clock broadcast's fixed block, and screen images, themes switched from the plugin, or carousels. The AIO screen keeps every saved setting and hides only the live figures; the LCD FLEX screens get their saved theme and its colours, data source, brightness and direction and the date and time, with the PC's figures zero.
- **Rendering new effects.** The plugin replays what L-Connect saved; it cannot compose a look. An LCD FLEX fan's wireless theme, its colours (`0x28`) and the switch onto it (`0x29`) are settings, not rendered content, and are sent: see "The clock's screen block".
- **The suspend-time save**, since FanControl does not tell a plugin the machine is suspending.
- **The screen, radio and light switches** (`0x16` reboot LCD, `0x23` close wifi, `0x26` light switch, and `0x27` switched _off_: the plugin only hands lighting to the motherboard, never takes it back), firmware updates, and more than one TX/RX pair.
- **The record's other flag and firmware bits** (the RPM high nibbles beyond `IsSyncMbLight` and the theme switches): masked off, decoded from nothing.

## Where the plugin departs from L-Connect 2.1.29

Everything above follows 2.1.29 except these, which are intended:

- **The PC's figures in the clock block are zero**, not L-Connect's idle 20 or its live values (see "The clock's screen block").
- **The screen table is filled from the saved template whether or not the group is in advance mode**, since the plugin cannot know what L-Connect last applied.
- **A device whose remembered receiver slot is outside 1-13 is not moved onto a free one.** 2.1.29's correction re-slots it (`GetRxUnused`); that is a bind, and the plugin never binds.
- **A ghost address is not refused on first sight.** 2.1.29's `RefreshList` calls `IsErrMac` for a newly heard device and, when a `0x01...` address matches an existing device's in bytes 1-5, puts the _existing_ device's address on its error list and `continue`s without advancing the record offset, so its loop re-parses the same record for ever and the wireless loop hangs. The plugin keeps the earlier rule: a ghost is settled after four reads of receiver slot conflict, and the ghost's own address is the one refused.
- **The table's second removal pass after the records is not run**: it can find nothing the pass before the request did not.
- **`LWirelessFanType`'s renumbering** is L-Connect's own migration problem (its enum gained members in the middle, so a case or fan document written by 2.1.11 reads back under other types in 2.1.29, and an upgraded Lancool 217 configuration gets no case speed from L-Connect at all). The plugin does not read those documents, so nothing to copy.
- **The theme switch sets every fan's bit** where 2.1.29's `TryRestoreWirelessThemeSwitches` converts the fan index twice and can set another fan's (see "The clock's screen block"); its readback is four list reads (four seconds at one a second) rather than twenty 200 ms polls, and the save after it is the plugin's one-send save.
- **The lighting handover (`0x27`) goes out at every build**, since the plugin is built on every FanControl refresh, where L-Connect sends it only on a resume; it is the same command, and the device acknowledges it. It is confirmed by the record's `IsSyncMbLight` bit with the theme switch's rounds and readback, where L-Connect only logs the bit; and the device's synced effect is streamed as L-Connect streams it.
- **The change marker after the screens' theme colours (`0x28`) is taken from the round's sequence** , not drawn at random, which is a different value for each round as L-Connect's is. The colours themselves go out as L-Connect sends them, when the service starts and again when the transmitter dongle is plugged in again, never for a group that comes back on its own (see "The clock's screen block"); a settings change made in L-Connect, which sends them again, is one the plugin never sees.
- **A group whose screen table entry another group's wrote over, on a receiver slot the two share, is not coloured while that lasts.** 2.1.29 writes both entries over the one slot, the later in its table order winning, and sends each group its colours and its theme switch regardless; the plugin sends the theme switch as L-Connect does, but colours only the group whose own entry went out, since the other's screens have not been told the theme its colours are for, and colours that group once its entry does go out (see "The clock's screen block").
- **A transmitter fault the transport reopens on the same path counts as the transmitter plugged in again.** L-Connect's service rebuilds its controller only on the USB watcher's removal and insertion; the plugin cannot tell a failed transfer that re-enumerated the dongle from one that did not, so it sends the two looks again after any loss of the transmitter's handle: what L-Connect does where the dongle was re-enumerated, and where it was not, one extra round of each look, which the device acknowledges as it did the first.
- **The commands under a sequence go one at a time per device**, where `SyncControlInfo` sends every pending one in the same pass under one shared sequence and ends them all on its acknowledgement; the bytes of each are L-Connect's, a later command starts at most a round after the earlier one ends, and a lost command is never taken for acknowledged by another's sequence.
- The timing differences of the section above: one list read a second, not three or four.
