# Architecture

The plugin is layered so that the only Windows-, USB-, and FanControl-specific code lives at the edges. The core - the byte encoding and the control loop - is pure and testable without hardware.

## Layering

The code is organized into these layers, each depending only on the ones below it:

- **Plugin** - the FanControl integration surface. Implements the host's `IPlugin3` contract, registers sensors and controls, and translates host callbacks into device commands. This is the only layer the host sees.
- **Worker** - the keepalive control loop that periodically re-asserts manual mode and pushes the current duty so the controller does not fall back to its firmware curve. It owns and drives the `Devices` beneath it.
- **Devices** - per-family device models that bind a `Protocol` encoder strategy to a concrete controller (PIDs, channel count, register map). This is where the family differences (SL vs SLI vs SL v2 and so on) are resolved. It also owns the injected clock (`IClock`) and the pure `ChannelWriteDecision` that drives the keepalive staleness check.
- **Transport** - the USB layer. Owns device enumeration, open/close, and the raw read/write, behind the `IDeviceTransport` seam (below). There are two transports: HID through `hid.dll`, on handles the plugin opens itself, which is every wired controller, and WinUSB for the L-Wireless dongles, which are not HID devices at all. Enumeration also collapses the several HID interfaces one physical controller can expose into a single logical device (see "Device identity and binding stability" below).
- **Protocol** - pure functions that encode commands and decode telemetry to and from HID report byte buffers. No I/O, no state, no clock. See `docs/protocol.md` for the full byte-level contract.
- **Logging** - a thin logging abstraction so the layers above can record diagnostics without binding to the host's logger type directly.

## The IDeviceTransport seam

All USB access goes through a single interface, `IDeviceTransport`. Two implementations sit behind it - one over the platform HID library, one over WinUSB - and nothing above `Transport/` knows which it is holding; tests substitute a fake that records the bytes written and replays canned read buffers. Because every layer above depends on the interface and never on a concrete transport, the entire protocol and control stack can be exercised on Linux/WSL in unit tests with no device attached. This seam is the single most important testability decision in the codebase.

## Pure-encoder strategy pattern

Each device family encodes set-speed, manual-mode, and ARGB-sync reports differently (different duty-to-byte formulas, different register bytes, different RPM offsets). Rather than branch on family inside the device or worker code, each family is represented by a pure encoder strategy: a stateless object that maps high-level intent (set channel N to D percent duty) to the exact byte buffer for that family. The encoders are pure functions of their inputs - no clock, no I/O, no mutable state - so they are trivially unit-testable and the family-specific bugs documented in `docs/protocol.md` are pinned by direct assertions on the produced bytes. The ARGB-sync encoder exists for every family, but its one call site (in `FanController`) is compiled in only for the ARGB build variant (`-p:EnableArgb=true`, the `ENABLE_ARGB` symbol); the standard build never emits it. See `docs/protocol.md` for the variant's behavior and trade-offs.

## Clock-injected keepalive worker

The keepalive worker takes its clock as a dependency rather than calling the system clock directly. Injecting the clock makes the loop deterministic in tests: a fake clock can advance time instantly and the test asserts exactly which reports were emitted on each tick, with no real waiting. In production the clock is the real monotonic clock and the loop runs on its own background thread.

## How FanControl drives the plugin

These are FanControl's own rules, read from its code (the service and library of V278, checked against V243 and V242), and the plugin is shaped around them:

- **A new plugin object on every refresh.** Each `Initialize` of FanControl's device layer reloads plugins, and its loader creates the plugin type afresh; only the assembly stays loaded. Anything kept on the plugin object is gone at the next refresh, which FanControl runs at startup, about five seconds after every resume, and whenever a plugin asks for one.
- **`Close` only for an instance that registered sensors.** An instance that found nothing useful is dropped without `Close`, so whatever it started keeps running.
- **`Update` holds the lock that serialises every device FanControl drives.** Time spent in it is time the whole application stands still, and so is time spent in `Initialize`.
- **`IPlugin3` lets a plugin ask for a refresh.** FanControl answers `RefreshRequested` with a full `Close`, `Initialize` and `Load`, trying at most twice, three seconds apart, and stopping at the first that succeeds. The refresh is FanControl-wide: every sensor source is closed and initialised again, LibreHardwareMonitor and the GPU libraries included, and fans are released while it runs, so the plugin asks for one only when nothing else can register a sensor (see below). It arrived in V243, which is therefore the oldest FanControl the plugin loads into. On V242 and older the loader cannot resolve the interface, and because its `Assembly.GetTypes()` call is unguarded and shares a `try` with the rest of initialisation, FanControl then loses every sensor source, not just this one. The README states the minimum for that reason.

So what must outlive a plugin object lives in `PluginRuntime`, one per process: the worker that is running and the controllers it drives, and every controller the process has built. Each `Initialize` first stops whatever is running - its own last run, or that of an earlier instance nobody closed - and `Close` stops it only if the runtime is still its own. `Update` does no device I/O at all: the worker does every transfer, with one `ControllerLoop` per controller on a thread of its own, so a controller stalled in a bounded but seconds-long call (a reopen after a wake, a transfer running out its timeout) delays nothing but itself. Each loop ticks once a second, and at once when a control's target changes (`ControlSensor.Set` wakes the loops, and only for a value that differs from the last). Stopping tells every loop at once and then waits for them all out of one two-second budget. `Update`'s one job is to raise `RefreshRequested`, on FanControl's own thread, when the runtime has been asked for a refresh - a wireless device checked in after the scan, or a controller finished opening after the scan had given up on it - and no more often than every thirty seconds.

`Initialize` itself is bounded as a whole: `ControllerBuilder` builds every controller the scan planned side by side, on threads of its own, under one five-second deadline, so a wake that leaves several controllers wedged costs one timeout rather than one each. A build that is still running at the deadline is abandoned to its thread. If it finishes, the controller is remembered, so any later scan that finds it slow stands in for it, and it is handed to the stand-in this scan registered for it, if there is one that has not connected by itself meanwhile, so the device is not opened twice. Only a controller no scan had built before has no stand-in, and only then is a refresh requested - once per new device, however often it is slow - since a refresh costs FanControl every source it has.

Each `Initialize` runs under FanControl's own device lock, which its update loop also takes, so the host's readings pause while it runs. Every step is bounded: stopping the previous worker takes at most two seconds, the device scan five, and the builds five, so a wake that leaves every device wedged costs FanControl at most about twelve seconds of the plugin's own waiting, once, rather than the frozen window of #34 (FanControl's own HID scan is another matter; see "The IDeviceTransport seam").

## Handle fault recovery across sleep and hibernate

The HID handles the transport opened at startup have to outlive every USB re-enumeration the machine goes through: S3 sleep and hibernate (Windows Fast Startup hibernates the system session rather than shutting it down, so it may look the same to a plugin that survives it; either way the recovery below covers it). FanControl does close and re-initialise every plugin a few seconds after a resume, but nothing re-initialises the plugin after any other re-enumeration, and the fans are uncontrolled until a refresh happens, so the transport recovers on its own. Across each of those the controller is re-enumerated underneath the old handle, and the first transfer on it either hangs (the bounded control transfer times out) or fails with a device-gone error. The transport treats any of those as a **handle fault**: it latches the fault so later transfers fail fast instead of each spawning a new watchdog, and it then reopens the device on its original path from the worker path - the path is stable across re-enumeration on the same port - swapping in a fresh stream and input handle. Reopens follow the pure `DoublingBackoff` schedule (in `Transport`): immediately on the first faulted transfer, so a transient fault costs no dead time, then after a gap that doubles up to about five minutes, so a controller that is genuinely gone is probed occasionally rather than every tick. The transport has no clock (the injected clock lives above the Transport layer), so the schedule counts faulted transfers - two per controller per one-second tick - rather than seconds. A successful reopen is logged (`reopened <path> after N faulted transfer(s)`); a failed attempt keeps the fault latched and surfaces through the worker's per-controller catch like any other transfer error. Above the transport, each controller records the transport's `Generation` (bumped on every successful reopen) when it sets the device up; on the first `ApplyPending` after it moves on, the controller replays its setup in the order Initialize used - the Lighting build's saved look and the manual-mode assert (with the ARGB sync in the ARGB build) for a Uni controller, software control then the look for a TL hub, the look alone for a Galahad - and re-sends every channel's duty, because a device that was re-enumerated may have been power-cycled and lost all of that volatile state (hibernate does exactly this). The composition root registers the look replay through `IFanDevice.ReplayOnReconnect`, so lighting stays a Plugin-layer concern and the replay runs on the worker thread like every other transfer. The backoff, the fault latching and the reopen are unit-tested through a fake of the native HID surface (`IHidApi`, `IHidTransfer`); only the thin adapter over `hid.dll` and `kernel32` itself (`WindowsHidApi`) needs Windows, and the Windows-only tests run it against whatever HID devices the machine has.

## Every wait on the device is bounded, on every thread

A controller can come back from sleep wedged: still present to Windows, but never completing an open or a transfer on it. Nothing in user mode can make such a device answer, so the plugin's job is to make sure no thread waits on it without a deadline - least of all one the host is waiting for. FanControl closes and re-initialises every plugin about five seconds after a resume, on a refresh thread that holds its engine clock while it runs; a plugin that blocks that thread leaves FanControl behind a blank window until the machine is rebooted, which is what a wedged controller did once every ten or so sleeps (#34): the worker's reopen blocked on the device, then the refresh's `Close` waited on the worker and its `Initialize` on the device scan, which opens the same device.

So every call that reaches the device runs under `BoundedDeviceCall` (in `Transport`), on a throwaway thread with a deadline: a control transfer for 500 ms; an interrupt transfer on the HID stream handle (the TL and Galahad command packets) for one second, inside which the transport waits 500 ms for the overlapped `WriteFile` or `ReadFile` itself, cancels it with `CancelIoEx`, and waits 400 ms more for the driver to complete the cancel, leaving the transfer's memory to the kernel if it never does; a WinUSB write for one second and a read for 500 ms plus 50 ms for every packet it may read (those asked for, eight more of drain allowance, and the one that ends the reply); a reopen - the close of the stale handles and the fresh open together, since either can block - and a close for two seconds; the device scan in `Locate` for five seconds and an `Open` for two. On timeout the call's token is cancelled first, then its pending I/O - by handle (`CancelIoEx`) where there is one, by aborting both pipes for a WinUSB dongle (itself bounded, falling back to `CancelIoEx`), and by thread (`CancelSynchronousIo`) always - so a blocked call unwinds instead of pinning a handle, and a timed-out transfer faults the handle so the reopen path takes over. The call is then abandoned to its thread. Every call that makes more than one native call checks its token before each, so an abandoned one stops at its next native call instead of making one that nothing would cancel: the flush then write of a WinUSB write, the open then setup of an open or reopen, the pipe after pipe of an abort, and the device after device of a scan all stop where they were given up on. Closing a handle is the one step that never stops for the token, since a handle left to its finalizer would be closed on the host's single finalizer thread, where the same wedged close would block for good. Whatever that thread eventually opens is handed back through `OpenHandoff`, which disposes it on the spot if the caller has already gone, and an exception it throws after the caller gave up is logged rather than lost (the cancellation its own token raises, the unwind that was asked for, is not). Those cancels usually unwind an abandoned thread within milliseconds, but a `CreateFile` or configuration manager call blocked inside the kernel may never return, and the reopen backoffs, the stand-in rebuilds and the host's retried `Initialize` keep trying that device for the life of the process, so each retry would otherwise strand another thread. So every bounded call goes through `DeviceCallGate` (in `Transport`), keyed by device path without regard to case and shared by the enumerator and every transport it opens, with the scan under a key of its own: the bound reports when an abandoned call is finally done with, and until then any new call to that device fails fast with an `IOException` naming the earlier call and how long ago it was given up on, before any thread is created. The refusal is logged once per stuck episode (`<operation> refused: the earlier <operation>, given up on N ms ago, has not returned; ...`), and once the stuck call returns the device is reachable again, with a line saying so if anything was refused (`<operation> returned N ms after it was given up on; calls to <path> resume (M refused meanwhile)`). A close and a pipe abort still run while a call is stuck, since they only release or cancel what the device already holds and neither can pile up. A device that stays wedged therefore costs at most one stuck thread, not one per retry. A transport's `Dispose` never throws: it runs on the plugin's own threads as well as the host's, where an exception would end the FanControl service, so a close that fails is logged and left to Windows like one that times out. A timed-out scan fails that `Initialize` with the remembered controllers stood in for; every build in `Initialize` shares one deadline (see above); and stopping the worker waits for all its loops out of one two-second budget, each loop releasing its own controller if it is still inside a device call when the budget runs out. The bounds, the cancel choices, the tokens, the handoffs and the loops' disposal are unit-tested through fakes of the native calls (`IDeviceCallRunner`, `IDeviceCallClock`, `IHidApi`, `IHidTransfer`, `IWinUsbApi`, `IConfigurationManagerApi`), whose runner can land a deadline inside any one native call and hold an abandoned call until a test lets it return; what needs hardware is only whether a wedged device actually honours a cancel. The gate's record of stuck calls is the process's, not the plugin object's, since FanControl makes a new plugin object on every refresh while a call it gave up on is still stuck. The gate also holds one claim per open device path for the whole process: FanControl gives the previous plugin object's controllers only a bounded time to stop, and one still mid-transfer - a lighting stream takes seconds - can outlive it, so a path is not opened again until its previous owner has closed it, and two owners never write to one device at once. An open refused that way fails like any other, and the device is stood in for until a rebuild finds it free.

None of this goes through a library the host shares. FanControl ships HidSharp and uses it itself - LibreHardwareMonitor's AquaComputer group lists HID devices through it while FanControl holds the lock that serialises every device it drives - and HidSharp's device list is process-wide: a scan takes a process-wide lock, opens each newly seen device on thread-pool threads, and waits for all of them with no deadline. A controller that wedged inside that fan-out would leave the lock held after the plugin's own deadline had returned, and the host's next HID scan would block behind it for good, freezing FanControl. So the plugin does its own enumeration and its own I/O: the configuration manager's list of present HID interfaces (`CM_Get_Device_Interface_List` for the class `HidD_GetHidGuid` names); a handle with no access rights for `HidD_GetAttributes` and `HidP_GetCaps`, opened only on an interface whose path names a device the plugin drives, so no other device can hold up a scan; and overlapped `WriteFile` / `ReadFile` on a stream handle it owns, each waited for with its own deadline. All of it runs on the plugin's own threads, holding no lock anything else could need. What the plugin cannot do is bound FanControl's own scan: LibreHardwareMonitor still lists HID devices through HidSharp, which opens every interface it has not seen before, so a controller that comes back from sleep truly wedged can still hold FanControl up through that scan, with no plugin code involved. The plugin's log tells the two apart, since every call it gives up on is logged with what it was waiting for. The configuration manager spells a path with the device instance's capitals, where the setup API every earlier release enumerated through reports it in lower case; the path is kept in lower case, because it is also the controller's identity (see "Device identity and binding stability" below).

## The wireless fans: two WinUSB dongles as one controller

The wireless UNI FAN range is driven through the L-Wireless SYNC controller's transmitter and receiver dongles, which Windows binds to WinUSB, so they have no HID interface to list. `WinUsbDeviceLocator` (in `Transport`) finds them the way Lian Li's own software does - walking the present USB device instances, reading the interface GUID each one's driver registered in its hardware key, and resolving that to a path - because the generic USB device interface every USB device exposes belongs to the hub stack and cannot be initialised as WinUSB. The enumerator opens the result with `WinUsbTransport`, a second `IDeviceTransport` over `winusb.dll` whose `Write` is one OUT transfer and whose `Read` gathers IN packets until the dongle stops sending, draining a reply to its end as L-Connect's `WinUsb.ReadAll` does and discarding (and logging once) whatever arrives beyond the length asked for; it bounds every call exactly as the HID transport does, and it faults - and so reopens on the same backoff - on any failed or short write, after the 300 ms pause Lian Li's own software takes before reopening, and on a read whose native call outlives its bound. A reply that simply does not come fails that read and nothing more, as in L-Connect.

`WirelessController` (in `Devices`) owns the pair, because neither dongle is useful alone: the transmitter carries every command out and the receiver is the only way anything comes back. It is built on L-Connect's own model (`MasterDevice`), described in full in [wireless.md](wireless.md): a `WirelessDeviceTable` of every device heard, in first-heard order, updated from every list the receiver returns; a one-second cycle, on the injected clock, that re-sends each driven device's speed when what it reports differs from its target, queries the master (which also re-asserts the RF channel), refreshes each driven water block's screen and pump block, and broadcasts the clock; and the saved lighting replay in the Lighting build. Its construction never fails over a silent or late dongle - it retries for a bounded couple of seconds and then keeps trying in its cycle - and a device heard after construction that needs sensors raises `TopologyChanged`, which the plugin turns into a FanControl refresh. One control drives a whole fan group, as in L-Connect, and every fan reports its own speed through `IFanSpeedSource`; every sensor id is keyed on the device's RF address, so a device added later does not re-key the others. Each device's work in a tick is isolated from the others', every L-Connect settings file is optional to fan control, and `WirelessDonglePair` resets a dongle through its partner after five failed writes, as L-Connect does.

## Keeping a controller's sensors when a scan cannot reach it

FanControl registers sensors only when the plugin initialises, so a controller missing from one scan is missing from the host's list until the next refresh, and a user's fan curve bound to it is orphaned in the meantime. That is a real outcome of the bounded waits above: a scan that runs out of time reports nothing found, a device that will not open is skipped, and a device that has not re-appeared after a wake is simply not listed.

The runtime therefore remembers, for every controller the process has built, a `ControllerPlan` - what kind of controller over which located device(s), rather than a closure over the plugin object that built it, since that object is gone by the next refresh - together with the index it was built at and the sensors it registered. When a scan fails, when a planned device fails or is still opening at the deadline, or when a remembered device is simply absent from an otherwise good scan, the plugin registers a `ReconnectingFanDevice` in its place: the stand-in carries the exact channel and temperature identities the controller had, so the same sensors appear and the bindings hold, and it rebuilds the real controller through the current plugin object on the shared `DoublingBackoff`, on a thread of its own so a device that takes seconds to answer delays nothing but itself. Once built, it matches the rebuilt controller's channels to the remembered ones **by control id rather than by position**, so a device that came back with one fan missing leaves that one channel reading nothing instead of shifting every other channel onto the wrong fan. Targets the host set while it was disconnected are handed over on the rebuild, and a rebuild that finishes after the stand-in was disposed disposes what it built.

The same stand-in covers a controller that does build but comes back **incomplete**: a wireless dongle that opens before its fans have checked in over the radio after a wake, or a wired fan that happens to be stopped while its channels are probed. When a freshly built controller lacks any sensor it registered before, the plugin registers the union of the two through a stand-in wrapped around the new controller, so the missing sensors stay registered and read nothing until the device reports them again. Each remembered sensor carries when a build last reported it, and one that no build has reported for thirty days - a fan unplugged, a wireless group unbound in L-Connect - is let go, the same window a whole controller gets. So a fan stopped by its curve, or a PC off for a holiday, keeps its bindings, and hardware that is gone for good stops showing as a fan reading nothing.

A controller is remembered under the path of its first device, which is where it is plugged in: a Lian Li controller has no serial of its own to tell it by (every Uni unit shares one). So when a scan plans a device on a path nothing is remembered under, it first looks for a remembered controller of the same kind and product id that this scan did not find, and the new path takes that one over, lowest index first: its index, so its wired sensor ids, and its sensors. A controller moved to another USB port, or re-pathed by a hub or driver change, keeps its bindings instead of appearing twice - once live under new ids and once as a stand-in for a path that no longer exists. For the wireless pair, which is keyed on its transmitter, this also means at most one pair is ever registered, as L-Connect drives one.

What is remembered also outlasts the process. The runtime saves it after every scan to `remembered-controllers.json` beside the plugin's log (`RememberedControllerFile`, written whole to a temporary file and swapped in) and reads it back on a process's first `Initialize`. This matters because FanControl only listens for a plugin's refresh request once the plugin has registered at least one sensor: after a reboot on which nothing answers during the scan - wireless dongles slow to start, say - a plugin with nothing remembered would register nothing and so could never ask for the refresh that brings its devices in. With the file, the devices of the last run are stood in for from the start, their sensors registered and bound, and they connect as they answer; a HID device remembered only by its path is found again among the interfaces Windows lists. A controller no scan has built for thirty days is let go, and so is a sensor no build has reported for thirty days; each is saved with its own time. The file is the plugin's own record, not a setting: one that is missing or not what the plugin writes is logged and treated as empty. One that cannot be read at that moment (locked, say) is read again at the next `Initialize`, and nothing is saved over it meanwhile. The scan that ran without it numbered its controllers blind, so when the file is read the file wins: a saved controller keeps its saved index and every sensor it saved, a guess that took a saved index is let go and numbered again, and a build still running from before is neither remembered at its guessed index nor allowed to hold it (`PluginRuntime.NumberingEpoch`).

A controller also keeps its **index** - across runs, through the same file: the wired sensor ids are keyed on it, so the runtime hands a remembered device back the index it first had, and a new device the lowest index no remembered one holds. The first scan of a process numbers controllers in device-path order exactly as before any were remembered, so existing bindings are unchanged; later scans can no longer give a new device the index a missing one's stand-in is using.

## Device identity and binding stability

FanControl persists a user's fan-curve bindings against each sensor's `Id`, so those ids must mean the same physical channel every time the plugin loads. Two enumeration facts work against that, and the Transport/Plugin layers handle both before any sensor is registered:

- **Duplicate HID interfaces.** A composite controller can surface more than one matching HID interface (top-level collection) under the same vendor/product id, which would otherwise register a duplicate Ch1-4 sensor set per interface. `HidDeviceDeduplicator` (in `Transport`) collapses interfaces that share a Windows ContainerId down to one logical controller, keeping the interface that accepts the largest output report (the fan-control collection). The USB serial is deliberately not the key: the Lian Li Uni controllers all report the same firmware-fixed serial, so a serial key would wrongly collapse distinct controllers into one - the ContainerId, which every interface of one physical device shares and which differs across devices, does not. The grouping is deliberately conservative: a device whose ContainerId could not be resolved is never collapsed (it keys on its per-interface device path), so two distinct controllers are never mistaken for one - the safe failure direction. The helper is pure, so the grouping is unit-tested without hardware.
- **Unstable enumeration order.** The OS does not guarantee a stable order across reboot/sleep/hibernate for two identical controllers, and the sensor id is keyed on the controller's index. The plugin therefore orders the located controllers by their OS device path (ordinal) before indexing, so the same physical port keeps the same index - and the same sensor id - run to run. A single-controller setup is unaffected; this only matters when two or more identical controllers are present.

Enumeration itself runs behind a host-seam resilience guard: the first access to the HID device manager can fail in some host/desktop contexts, so a failure there is logged and degrades to zero controllers rather than propagating into FanControl and crashing it - the same resilience the per-device open path already applies, one level up.

Construction of a `FanController` performs no device I/O. Its one-time setup writes (the manual-mode assert, and the ARGB-header sync in the ARGB build) live in `FanController.AssertManualMode()`, which the composition root calls after registering the controller, behind its own resilience guard. This ordering is deliberate: a hub whose firmware or HID interface rejects a setup write (a hardware family the setup path was never verified on, a stalled control transfer) must degrade to a logged fault on an otherwise working controller, never to the controller silently vanishing from FanControl. Recovery is free because the worker re-asserts manual mode before every speed write anyway.

## Channel population detection

A UNI FAN controller always has four channels in firmware, but a user rarely fills all four; surfacing the empty ones as dead controls clutters the UI. The controller reports no presence bit - its input report carries only RPM - so the plugin infers which channels have a fan from a short burst of RPM probes at startup: a channel that reads a plausible, non-zero RPM on a strict majority of probes is populated, an empty channel reads zero or occasional out-of-range garbage. The decision is a pure function (`ChannelPopulationDecision`, in `Devices`), so the majority rule is unit-tested in isolation; the probing itself is a public `FanController.DetectPopulation()` the composition root calls once after construction (never in the constructor, which would make construction do I/O and block a gated test read), guarded so a probe fault leaves the controller fully shown rather than lost. `Load` then registers sensors only for populated channels, skipping the empties via the `IsChannelPopulated` seam (the TL and Galahad II controllers, whose channels are all physical, always return `true`).

Two safeguards keep this from ever hiding a real fan: if _no_ channel looks populated the result is treated as inconclusive and all four are shown, and detection runs before the plugin drives anything, when a present fan still idles at its non-zero firmware default. The one residual limitation is a fan that is present but deliberately stopped (a 0rpm-capable fan the user has stopped) at probe time - indistinguishable from an empty channel, so it stays hidden until it next spins. Hiding a channel is safe for a user's saved config: FanControl resolves each binding independently and greys out (and later re-links) a binding whose sensor is absent rather than rejecting the whole configuration, so the populated channels' bindings are untouched.

## Minimal public surface

Only the plugin entry type is `public`; everything else (Transport, Protocol, Devices, Worker, Logging) is internal. FanControl discovers plugins by scanning the assembly for the public type that implements its plugin interface, so exposing anything more would only widen the API the host could accidentally bind to and the maintainer would have to keep stable. Keeping the surface to a single public type means the internals can be refactored freely without affecting the host contract.
